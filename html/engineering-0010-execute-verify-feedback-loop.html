AI 参考答案Claude-Opus-4.82026-08-06

本质：验证是把「工具返回值」升级为「对世界真实状态的独立复核」。 工具返回 200/OK 只代表调用被接受，不代表副作用如预期发生。执行-验证-反馈闭环让 Agent 用一次独立的读回确认结果，再决定收尾、重试还是升级——这是所有有副作用的工具都该配的能力，写代码跑测试只是其中一例。

通用套路：动作 → 读回真实状态 → 与预期断言 → 命中则结束/不命中则修正。

场景 验证动作 收益
数据库变更 commit 后从 authoritative（读己之写一致）源读回、affected_rows、约束/行数校验 抓住写错行、静默失败
文件操作 重读内容、校验和、lint/parse 防写坏、路径写错
UI 自动化 截图/DOM 断言目标元素出现 防「点了但没生效」
邮件/消息 查 provider 上报状态：accepted / delivered / bounced / read 逼近而非等同「真的送达」
支付/转账 回查订单终态、对账 防重复扣款、状态不一致
基建变更 health check、金丝雀探测 防上线即故障

成本：每次验证都要额外读回，带来延迟、调用费、token 和实现复杂度；对高频低风险动作全量验证并不划算。按「误判代价 × 频率」定验证强度——低风险抽样，高风险必验。

风险边界（关键）：别把「能不能验证」和「能不能重试」混为一谈。验证策略沿三条正交的轴设计：

  • 结果可观测性（outcome observability）：能否读回真实终态？能读回才能验证；发短信这类无回执的动作弱可观测，只能靠 provider 上报或对账逼近。
  • 重试安全性（retry safety）：由幂等性 / 去重决定，而非「可逆」。带幂等键或去重窗口时，重试不会造成重复扣款/重复发信——即便动作本身不可撤销，重试也安全。
  • 可补偿性（compensability）：结果能否被撤销或补偿？DB 可回滚、转账可发起冲正属可补偿；已投递的邮件不可撤销，只能靠后续补偿动作（撤回请求、更正邮件）兜底。
动作
 ├─ 可观测? ──否──► 弱验证：只能对账/告警，无法即时确认
 │        └─是──► 读回终态断言
 ├─ 幂等/去重? ──是──► 失败可安全重试
 │            └─否──► 重试前先加幂等键，否则重复副作用
 └─ 可补偿? ──是──► 失败可回滚/冲正
             └─否──► 重心前移：dry-run + 二次确认 + 审批

对不可撤销或补偿不完整的副作用，安全控制应前移到执行前——幂等键、预演、审批；事后仍按可观测性回查 provider 状态 / 订单终态（这本身就是 verification），只有低可观测或状态不一致时才退化为对账与告警。支付的可补偿性要按退款、冲正等具体能力判断，而非一律当作不可补偿。一句话：凡有副作用的工具都值得配读回验证，但验证强度按「结果可观测性」定，重试策略按「幂等/去重」定，回滚兜底按「可补偿性」定，三者各管一段，别用「可逆」一个词一刀切。

追问 01

验证本身也可能失败或说谎（读到脏缓存、验证器有 bug），怎么防止 Agent 陷入「假验证」而误以为成功？

展开追答：验证本身也可能失败或说谎（读到脏缓存、验证器有 bug），怎么防止 Agent 陷入「假验证」而误以为成功？
追答

三条原则：① 验证要「独立于执行路径」但仍读 authoritative 源——别用写入时同一个连接/缓存去读回，但也别读有复制延迟的从库/旁路 replica（会漏看刚提交的写入），应从 commit 后具备读己之写一致性的权威数据源复核；② 验证也要有兜底——验证超时/异常时按「未确认」处理并告警，绝不默认成功，宁可误报不可漏报；③ 断言要具体、可证伪——校验行数、关键字段、终态枚举等硬指标，而非「无异常即通过」，并给验证设最大重试与最终 SLA，防止验证环节自身死循环。核心：验证器的可信度也要被度量，高风险动作叠加人工抽检或双通道交叉核对。
