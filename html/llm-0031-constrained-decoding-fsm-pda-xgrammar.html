题目

约束解码（Constrained Decoding）是如何用有限状态机与下推自动机在解码期实现 100% 语法合法的，XGrammar 与 Outlines 如何消除词表掩码扫描开销？

大模型基础与原理困难工程师

在生产级 Agent 的工具调用（Function Calling）、数据抽取（JSON Schema）以及领域特定语言（SQL / DSL）生成中，仅靠提示词示范或事后正则提取仍难以杜绝括号未闭合、转义符错误或多余寒暄文本。为此，主流推理引擎（如 vLLM、SGLang、TensorRT-LLM）普遍引入了基于形式文法的约束解码（Constrained Decoding / Guided Generation），在自回归采样的每一个步长动态屏蔽违反语法的词表 Token。

然而，现代大模型的词表规模普遍高达 $|V| \approx 128\text{k}$，若每个生成步都在运行时用解析器遍历全词表，CPU 掩码计算开销将远超 GPU 算子耗时。请深入剖析：

  1. 约束解码是如何在 Logits 采样阶段通过二元掩码保障 $100%$ 语法合法的？Outlines 是如何将正则表达式与 JSON Schema 编译为有限状态机（FSM），并通过预处理词表索引映射 $\sigma: Q \to \mathcal{P}(V)$ 将单步掩码查询复杂度从 $\mathcal{O}(|V|)$ 降至 $\mathcal{O}(1)$ 的？
  2. 当目标格式从正则升级为包含任意递归嵌套的上下文无关文法（CFG，如完整 JSON、SQL、Python AST）时，为什么下推自动机（PDA）的栈状态无法全部离线预计算？XGrammar 是如何通过拆分“上下文无关 Token（Context-Independent）”与“上下文相关 Token（Context-Dependent）”、自适应掩码缓存及上下文扩展（Context Expansion）消除绝大部分运行时检查的？
  3. 在高吞吐推理引擎中，如何通过前跳解码（Jump-Forward Decoding）、CPU-GPU 异构流水线重叠以及“先推理后结构化”设计，兼顾生成吞吐与模型的语义推理质量？

约束解码的核心原理是“将形式语言自动机与自回归采样分布对齐”：在每个解码步 $t$，语法引擎根据已生成序列所处的自动机状态计算词表掩码 $m_t \in {0, 1}^{|V|}$，将所有会导致语法失配的 Token Logits 置为 $-\infty$，从而在数学上保证采样轨迹必为目标文法的合法前缀。在工程实现上，针对正则与扁平 JSON Schema，Outlines 利用确定性有限状态机（DFA）离线遍历词表构建状态到合法 Token 子集的哈希索引 $\sigma: Q \to \mathcal{P}(V)$，实现运行时 $\mathcal{O}(1)$ 查表；针对任意递归的上下文无关文法（CFG），XGrammar 构建字节级下推自动机（Byte-Level PDA），将词表拆分为仅依赖栈顶节点的“上下文无关 Token”（占词表 $>99%$，离线预计算并存入自适应稀疏/位图缓存）与跨越规则弹出边界的“上下文相关 Token”（占 $<1%$，经上下文扩展预过滤后配合持久执行栈在运行时快速校验），并将 CPU 掩码生成与 GPU 前向计算异步重叠，实现近乎零额外延迟的结构化生成。

现有 agent-0021 从应用层介绍了“生成端约束 + Schema 校验重试 + 括号配对提取”的三层防线，engineering-0018 讨论了流式结构化输出的增量渲染与容错契约，llm-0007 与 llm-0012 分别剖析了 BPE 子词切分与解码采样分布变换。本题聚焦推理引擎底层的约束解码算法机制：FSM 词表状态索引构建、子词跨语法边界的 PDA 栈拆分、XGrammar 自适应掩码缓存，以及强格式约束对模型推理分布的潜在影响与工程缓解。

1. 掩码采样数学形式与 Outlines 的 FSM 词表索引机制

为什么朴素全词表扫描会拖垮推理吞吐？

设大模型词表为 $V$（每个元素 $v \in V$ 是由基础字节/字符字母表 $\Sigma$ 组成的子词字符串，如 {"id": 或 123），词表大小 $N = |V|$ 通常在 $32\text{k} \sim 152\text{k}$ 之间。在自回归生成第 $t+1$ 个 Token 时，模型前向传播输出原始 Logits 向量 $\boldsymbol{z}_t \in \mathbb{R}^N$。

约束解码引入一个由当前已生成前缀 $S_t = (s_1, \dots, s_t)$ 决定的二元掩码函数 $m(S_t) \in {0, 1}^N$：若拼接子词 $v$ 后存在至少一条路径能够到达目标文法 $G$ 的接受状态（即 $S_t \circ v$ 是合法语言 $L(G)$ 的有效前缀），则 $m_v(S_t) = 1$，否则 $m_v(S_t) = 0$。修正后的采样分布为：

$$\tilde{z}{t,v} = \begin{cases} z{t,v}, & \text{if } m_v(S_t) = 1 \ -\infty, & \text{if } m_v(S_t) = 0 \end{cases}, \quad P(\tilde{s}{t+1} = v \mid S_t) = \frac{m_v(S_t) \exp(z{t,v} / \tau)}{\sum_{v' \in V} m_{v'}(S_t) \exp(z_{t,v'} / \tau)}$$

如果在每个解码步都对词表中全部 $N$ 个 Token 从头运行一次增量解析器（Naive $\mathcal{O}(N)$ Runtime Evaluation），单步 CPU 扫描耗时可达数十至数百毫秒，比 GPU 单步 Decode（通常 $5\sim 20\text{ ms}$）慢一个数量级以上。

方案维度 朴素运行时扫描（Naive Vocab Scan） FSM 预索引（Outlines / 扁平 Schema） 字节级 PDA + 自适应缓存（XGrammar）
形式语言表达力 任意增量解析器 / 正则 正则表达式（Regular Language，可覆盖无递归 JSON Schema） 上下文无关文法（CFG，支持任意递归 JSON、SQL、DSL）
底层自动机模型 每次从头或按字符步进解析 确定性有限状态机 $M = (Q, \Sigma, \delta, q_0, F)$ 字节级下推自动机（Byte-Level PDA + 持久树状栈）
预处理阶段工作 无 遍历词表 $V$ 与所有状态 $Q$，构建映射 $\sigma: Q \to \mathcal{P}(V)$ 规则内联 + 节点合并 + 预计算上下文无关掩码 + 扩展后缀提取
单步运行时掩码复杂度 $\mathcal{O}(|V| \cdot \bar{L}_{\text{tok}})$，随词表线性恶化 $\mathcal{O}(1)$ 哈希查表，直接取出当前状态 $q$ 的合法 Token 集 $>99%$ 词表直接查表 + $<1%$ 上下文相关 Token 栈校验
核心工程局限 高并发下 CPU 成为绝对瓶颈 复杂/深层递归文法会导致 DFA 状态数 $|Q|$ 爆炸甚至不可表示 动态 Schema 首次编译存在毫秒级预处理开销（需做 Schema 缓存）

Outlines：如何用自动机子序列匹配实现 $\mathcal{O}(1)$ 查表？

Willard & Louf (2023, Outlines) 指出，任何正则表达式或无无限递归的 JSON Schema 均可等价编译为一个确定性有限状态机（DFA）$M = (Q, \Sigma, \delta, q_0, F)$，其中 $Q$ 为有限状态集，$\Sigma$ 为字符/字节表，$\delta: Q \times \Sigma \to Q$ 为状态转移函数。

由于 LLM 的单个子词 Token $v = (c_0, c_1, \dots, c_{|v|-1}) \in V$ 往往包含多个字符（甚至跨越 JSON 键值边界，如 ":1），Outlines 在离线预处理阶段对每个词表 Token $v \in V$ 执行子序列遍历（原论文 Algorithm 3 & 4）：

  1. 枚举起始状态：找出所有能够接收 $v$ 首字符 $c_0$ 的状态 $r \in \delta^{-1}(\cdot, c_0)$；
  2. 沿自动机连续步进：从状态 $r$ 出发，依次按字符 $c_1, \dots, c_{|v|-1}$ 调用转移函数 $r_{k+1} = \delta(r_k, c_k)$；
  3. 构建索引表 $\sigma$：若整个子词 $v$ 的所有字符均未触发空转移（$\delta \neq \emptyset$）且最终到达状态 $r_{\text{end}}$（能够继续通向接受状态 $F$），则将 Token $v$ 加入起始状态 $r$ 的合法集合 $\sigma(r)$，并记录转移终点 $\tilde{\delta}(r, v) = r_{\text{end}}$。

在自回归解码时，若当前自动机处于状态 $q_t \in Q$，引擎无需再逐个检查词表，只需以 $\mathcal{O}(1)$ 复杂度读取预编译集合 $\sigma(q_t)$ 生成掩码；采样出 Token $\tilde{s}{t+1}$ 后，直接令 $q{t+1} = \tilde{\delta}(q_t, \tilde{s}_{t+1})$ 即可进入下一步。

2. CFG 递归结构挑战与 XGrammar 的字节级 PDA 优化

当业务需要生成无固定深度的任意合法 JSON（Recursive JSON）、嵌套表达式（SQL / Python AST）或递归自定义工具参数时，正则与有限状态机（FSM）因缺乏栈记忆无法匹配任意层级的括号配平，必须使用上下文无关文法（CFG）与下推自动机（Pushdown Automaton, PDA）。

为什么 PDA 不能直接照搬 Outlines 的全状态预计算？

在 PDA 中，解析状态不仅包含当前规则内的自动机节点 $q$，还包含一个记录父规则调用返回点的无界调用栈（Unbounded Stack） $S = (q_{\text{ret},1}, q_{\text{ret},2}, \dots, q_{\text{top}})$。由于嵌套深度在运行前未知，可能的完整栈组合数量是无穷大（或随深度指数级爆炸）的，不可能离线预计算所有栈状态下的词表掩码。更棘手的是，BPE 分词器的子词边界与语法规则边界完全解耦——例如一个 Token 1} 既包含了内层数字规则的字符 1，又跨越边界关闭了外层对象规则的 }；甚至有些多字节 UTF-8 字符被切成了不完整的半截字节 Token。

XGrammar 的四大核心算法机制

Dong et al. (2025, XGrammar, MLSys 2025) 针对上述难题设计了**字节级下推自动机（Byte-Level PDA）**与分层掩码架构：

                       词表 V (如 Llama-3 128,000 Tokens)
                                       │
         ┌─────────────────────────────┴─────────────────────────────┐
         ▼ (> 99% 词表: 仅依赖栈顶节点 q_top)                        ▼ (< 1% 词表: 触发弹栈回父规则)
  [上下文无关 Token (Context-Independent)]                   [上下文相关 Token (Context-Dependent)]
  1. 在当前规则内步进 (Advance within rule)                  匹配到当前子规则末尾后仍有剩余字符需退回父规则检查
  2. 压栈进入子规则 (Push into child rule)                             │
         │                                                             ▼
         ▼                                                    [Context Expansion 预过滤]
  [Adaptive Token Mask Cache (离线预计算)]                    提取父规则允许的 Expanded Suffix，淘汰 ~90% 伪候选
  - Accept-Heavy 节点: 仅存 Rejected 列表 + CD 列表                    │
  - Reject-Heavy 节点: 仅存 Accepted 列表 + CD 列表                    ▼
  - 均衡节点: 存 128K 紧凑 Bitset (总内存 160MB 降至 0.46MB)  [运行时 Persistent Execution Stack 校验]
         │                                                    仅对剩余 ~120 个 Token 在树状持久栈上动态验证
         └─────────────────────────────┬───────────────────────────────┘
                                       ▼
                     合并生成完整 Token Mask (CPU 与 GPU 前向异步重叠)
  1. 区分上下文无关（Context-Independent, CI）与上下文相关（Context-Dependent, CD）Token： XGrammar 洞察到，从栈顶节点 $q_{\text{top}}$ 开始匹配一个 Token 的字节序列时，栈转移只有三种情况：
    • 情况 A（深入子规则）：压入新返回点并跳入子规则内部；
    • 情况 B（当前规则内步进）：仅更新栈顶节点 $q_{\text{top}}$，不触碰栈底历史；
    • 情况 C（弹出当前子规则）：匹配到达当前子规则终点，必须弹出栈中保存的父规则返回节点才能继续验证该 Token 的剩余字符（如数字规则末尾遇到跨界 Token 1} 或 1,）。 关键定理：情况 A 和 B 的合法性完全由栈顶节点 $q_{\text{top}}$ 唯一决定，与调用栈下方的父规则历史毫无关系！因此这类 Token 被定义为上下文无关 Token（在 Llama-3.1 128k 词表的 JSON 文法下占比超过 $99%$，仅约 $1,134$ 个 Token 属于情况 C 的上下文相关 Token）。
  2. 自适应掩码缓存（Adaptive Token Mask Cache）： 既然 $>99%$ 的 Token 仅依赖有限个自动机节点 $q_{\text{top}}$，XGrammar 便以 $q_{\text{top}}$ 为键离线预计算它们的合法性。为避免每个节点都存储 $128\text{k}$ 长度的数组，XGrammar 根据每个节点的分流特征动态选择三种紧凑存储格式之一：
    • Accept-Heavy（绝大多数合法，如处于 JSON 字符串 [^"\\]* 内部）：只存少量的 Rejected CI Tokens 和 CD Tokens 索引列表；
    • Reject-Heavy（绝大多数非法，如刚读完 : 等待特定类型起始符）：只存少量的 Accepted CI Tokens 和 CD Tokens 索引列表；
    • 均衡节点：存压缩位图（Bitset）。在 Llama-3.1 JSON 基准下，该设计将掩码缓存内存从 $160\text{ MB}$ 降至 $0.46\text{ MB}$（压缩至 $0.2%$）。
  3. 上下文扩展（Context Expansion）与规则内联（Rule Inlining）： 对于情况 C 的上下文相关 Token，虽然在预处理时不知道运行时究竟是从哪条父路径调用进来的，但可以离线遍历整张 PDA 图，提取所有调用当前子规则 $R$ 的父节点之后可能紧跟的字符集合——称为扩展后缀自动机（Expanded Suffix，$\mathcal{A}_R^{\text{ctx}}$）。如果一个跨界 Token 在弹出子规则 $R$ 后的剩余字符串连 $\mathcal{A}_R^{\text{ctx}}$ 的任何前缀都匹配不上，则在预处理阶段直接将其判定为非法（CI_REJ）！配合小碎片规则自动内联（Rule Inlining），Llama-3.1 JSON 文法中真正需要留到运行时检查的 CD Tokens 数量进一步缩减了 $90%$（从 $1,134$ 个骤降至仅 $120$ 个）。
  4. 持久执行栈（Persistent Execution Stack）与 CPU-GPU 流水线重叠： 当文法存在非确定性分支或需要校验剩余百余个 CD Tokens 时，XGrammar 使用树状持久栈（Driscoll et al., 1989）共享历史栈前缀，实现 $\mathcal{O}(1)$ 指针级的分支分裂与回滚（这也天然适配投机解码 llm-0006 被拒绝时的自动机状态回退）。同时，由于第 $t$ 步的掩码计算只依赖第 $t-1$ 步已采样的 Token，引擎在 CPU 上异步计算第 $t$ 步掩码的同时，GPU 正在并行执行第 $t$ 步的 Transformer 层前向计算，仅在最后的 Sampler 核函数前同步拷贝掩码，从而将端到端 TPOT（Time Per Output Token）额外开销压至接近 $0$。

3. 可运行的标准库实现：字节级 PDA 词表分类、上下文扩展与前跳解码验证

以下 Python 3 标准库代码构建了一个包含主对象规则 $R_0$ 与数字子规则 $R_1$ 的字节级下推自动机，完整复现并验证了 XGrammar 的（1）CI_ACC / CI_REJ / CD 三类词表划分，（2）利用父规则扩展后缀集（Expanded Suffix）在预处理期直接淘汰非法跨界 Token 1,，以及（3）**前跳解码（Jump-Forward Decoding）**在确定性语法片段上跳过 LLM 前向传播的加速逻辑：

from typing import Dict, List, Optional, Set, Tuple

# 1. 构造描述简化 JSON 对象 {"id": <digits>} 的字节级下推自动机 (PDA)
# 主规则 R0 (OBJ): 0 --'{'--> 1 --'"'--> 2 --'i'--> 3 --'d'--> 4 --'"'--> 5 --':'--> 6 ==调用 R1==> 7 --'}'--> 8(接受)
# 子规则 R1 (NUM): 10 --数字--> 11(接受), 11 --数字--> 11(接受)
CHAR_EDGES: Dict[Tuple[int, str], int] = {
    (0, "{"): 1,
    (1, '"'): 2,
    (2, "i"): 3,
    (3, "d"): 4,
    (4, '"'): 5,
    (5, ":"): 6,
    (7, "}"): 8,
}
for d in "0123456789":
    CHAR_EDGES[(10, d)] = 11
    CHAR_EDGES[(11, d)] = 11

# 规则调用边: caller_state -> (callee_start_state, caller_return_state)
RULE_CALLS: Dict[int, Tuple[int, int]] = {6: (10, 7)}
ACCEPT_STATES: Dict[int, Set[int]] = {0: {8}, 1: {11}}
STATE_TO_RULE: Dict[int, int] = {**{s: 0 for s in range(9)}, 10: 1, 11: 1}

# 模拟子词词表 (包含跨语法边界的子词 token，如 '1}', '1,', '{"id":')
VOCAB: List[str] = [
    "{", '"', "i", "d", '"id":', '{"id":', "1", "23", "1}", "1,", "}", "abc"
]


def step_char(stack: Tuple[int, ...], ch: str) -> Optional[Tuple[int, ...]]:
    """在单字符 ch 下推进 PDA 栈 (栈尾元素为当前栈顶状态 q_top)"""
    curr = list(stack)
    while curr[-1] in RULE_CALLS:
        callee_start, ret_state = RULE_CALLS[curr[-1]]
        curr[-1] = ret_state
        curr.append(callee_start)

    top = curr[-1]
    if (top, ch) in CHAR_EDGES:
        curr[-1] = CHAR_EDGES[(top, ch)]
        return tuple(curr)

    # 若当前处于子规则接受状态且无法继续匹配 ch，则弹栈返回父规则状态再尝试匹配
    while len(curr) > 1 and curr[-1] in ACCEPT_STATES[STATE_TO_RULE[curr[-1]]]:
        curr.pop()
        top = curr[-1]
        if (top, ch) in CHAR_EDGES:
            curr[-1] = CHAR_EDGES[(top, ch)]
            return tuple(curr)

    return None


def classify_token_at_state(
    q_top: int, token: str, expanded_suffix_r1: Set[str]
) -> str:
    """
    按照 XGrammar 自适应掩码缓存机制对栈顶状态 q_top 下的 token 分类:
    - 'CI_ACC': 上下文无关接受 (仅靠当前规则内部转移或下推子规则即可判定合法)
    - 'CI_REJ': 上下文无关拒绝 (在当前规则内直接失配，或弹栈后违反父规则扩展后缀集)
    - 'CD':     上下文相关 (触发弹栈回父规则且剩余后缀符合扩展后缀，需运行时结合完整栈检查)
    """
    curr = [-1, q_top]  # -1 为调用方栈底哨兵
    popped_to_parent = False

    for idx, ch in enumerate(token):
        while curr[-1] in RULE_CALLS:
            callee_start, ret_state = RULE_CALLS[curr[-1]]
            curr[-1] = ret_state
            curr.append(callee_start)

        top = curr[-1]
        if (top, ch) in CHAR_EDGES:
            curr[-1] = CHAR_EDGES[(top, ch)]
            continue

        if top in ACCEPT_STATES[STATE_TO_RULE[top]] and len(curr) == 2:
            rem = token[idx:]
            # Context Expansion 预过滤: 弹栈后的剩余字符串必须匹配父规则扩展后缀集
            if rem in expanded_suffix_r1:
                popped_to_parent = True
                break
            return "CI_REJ"
        return "CI_REJ"

    return "CD" if popped_to_parent else "CI_ACC"


# 对子规则 R1 的状态 11 (已匹配至少一位数字):
# 父规则 R0 在调用 R1 返回状态 7 后仅允许字符 '}'，故 R1 的扩展后缀集为 {"}"}
EXPANDED_SUFFIX_R1 = {"}"}

cache_state_11 = {
    tok: classify_token_at_state(11, tok, EXPANDED_SUFFIX_R1) for tok in VOCAB
}
ci_acc_11 = [t for t, c in cache_state_11.items() if c == "CI_ACC"]
cd_11 = [t for t, c in cache_state_11.items() if c == "CD"]
ci_rej_11 = [t for t, c in cache_state_11.items() if c == "CI_REJ"]

# 验证 1: '1' 和 '23' 在子规则 R1 内部即可确认合法 (CI_ACC)
# 验证 2: '1}' 和 '}' 会触发从 R1 弹栈回父规则且剩余部分匹配 '}'，归入上下文相关 (CD)
# 验证 3: '1,' 虽前半部分 '1' 合法，但弹栈后 ',' 不在扩展后缀集 {"}"} 中，预处理直接剔除为 CI_REJ
assert ci_acc_11 == ["1", "23"]
assert cd_11 == ["1}", "}"]
assert cache_state_11["1,"] == "CI_REJ" and len(ci_rej_11) == 8


def advance_token(stack: Tuple[int, ...], token: str) -> Optional[Tuple[int, ...]]:
    s: Optional[Tuple[int, ...]] = stack
    for ch in token:
        if s is None:
            return None
        s = step_char(s, ch)
    return s


def run_constrained_generation() -> Tuple[str, int, int]:
    stack: Tuple[int, ...] = (0,)
    output = ""
    llm_forward_steps = 0
    jump_forward_chars = 0

    while stack != (8,):
        while stack[-1] in RULE_CALLS:
            callee_start, ret_state = RULE_CALLS[stack[-1]]
            stack = stack[:-1] + (ret_state, callee_start)

        # 检查当前状态是否只有唯一确定的单字符转移且不可直接弹栈结束 (Jump-Forward 条件)
        valid_chars = [ch for (st, ch) in CHAR_EDGES if st == stack[-1]]
        is_accept = stack[-1] in ACCEPT_STATES[STATE_TO_RULE[stack[-1]]]
        if len(valid_chars) == 1 and not is_accept:
            ch = valid_chars[0]
            stack = step_char(stack, ch)  # type: ignore
            output += ch
            jump_forward_chars += 1
            continue

        # 需要调用 LLM 采样: 计算当前全栈下的有效词表掩码
        valid_tokens = [t for t in VOCAB if advance_token(stack, t) is not None]
        assert len(valid_tokens) > 0
        # 模拟 LLM 在合法掩码下依次采样出数字 '23' 与跨边界闭合 token '1}'
        chosen = "23" if output.endswith(":") else "1}"
        assert chosen in valid_tokens
        stack = advance_token(stack, chosen)  # type: ignore
        output += chosen
        llm_forward_steps += 1

    return output, llm_forward_steps, jump_forward_chars


generated, llm_steps, jf_chars = run_constrained_generation()
assert generated == '{"id":231}'
assert llm_steps == 2 and jf_chars == 6

4. 生产级推理引擎中的工程权衡与架构实践

  1. 前跳解码（Jump-Forward Decoding / Compressed FSM）： 在严格的 JSON Schema 下，一旦生成了前一个字段，接下来的固定键名（如 {"id": 或 ", "status": "）在自动机上往往是一条没有任何分支的唯一确定路径。SGLang 与 XGrammar 支持在这些确定性区间直接由自动机拼接字符串并重新分词追加到上下文（作为一次小规模 Prefill），完全跳过逐 Token 的自回归 Decode 采样，大幅减少 GPU 访存步数。
  2. 语法编译缓存与扁平化 Schema 设计： 将复杂 JSON Schema 编译为自动机并构建自适应掩码缓存并非零成本——对于包含上百个字段或深层联合类型（anyOf / oneOf）的巨型 Schema，首次编译可能带来数毫秒至数百毫秒的首 Token 延迟（TTFT）抖动。工程上必须：（1）以 Schema 规范化哈希为键缓存已编译的 Grammar 对象；（2）避免在每次请求中将动态业务 ID 写进 Schema 键名或巨型枚举，改用扁平固定 Schema + 业务层校验。
  3. “推理质量退化”与两阶段解耦（Reason First, Format Later）： Tam et al. (2024, Let Me Speak Freely?) 的实证研究表明，如果强行要求非推理模型在第一个 Token 就进入严格 JSON 语法约束，模型无法输出中间推演步骤，在数学与多步逻辑任务上的准确率可能显著下降。解决这一矛盾有两条工程路径：
    • 原生推理模型（Reasoning Models）分段约束：在 <think>...</think> 思维链阶段保持无约束自由生成，仅当模型输出 </think> 进入最终答案阶段时才挂载 XGrammar / FSM 掩码；
    • 两阶段提取（Two-Stage Extraction）：对超大复杂表单（如从医疗病历提取 50 个字段），第一阶段让主力模型自由抽取完整的自然语言事实清单，第二阶段用轻量小模型开启约束解码将清单映射为严格 JSON。
  4. 切勿省略 stop_reason 检查： 即便开启了引擎级约束解码，以下两种情况依然会导致返回的文本不是合法 JSON：（1）输出达到 max_tokens 上限被硬截断（此时自动机尚未到达接受状态 $F$，JSON 停留在半截前缀）；（2）触发平台级安全拒答（如返回 stop_reason: "refusal"）。因此调用方在执行 json.loads 前，必须先校验 finish_reason / stop_reason == "stop" / "end_turn"（流式半截数据的处理详见 engineering-0018）。

常见误区

  • 误区一：“只要用了正则表达式做约束解码，就能完美处理任意 JSON 格式。” 事实：根据形式语言乔姆斯基谱系（Chomsky Hierarchy），正则表达式等价于 3 型正则文法（有限状态机），无法表达任意深度的括号配平与递归嵌套。只有当 JSON Schema 的字段、类型与最大嵌套深度全部静态固定时，才能展开为巨大的有限状态机；对于无 Schema 限制的任意合法 JSON、递归树节点或 SQL/Python 代码，必须使用 2 型上下文无关文法（CFG）与下推自动机（PDA）。
  • 误区二：“开启引擎级 JSON Schema 约束解码后，后端就不需要再做 try...except、Schema 业务校验或重试了。” 事实：约束解码只保证上下文无关的语法结构（Syntactic Validity）——而且当生成触及 max_tokens 截断或模型拒答时，连完整语法都会被破坏。此外，自动机无法校验跨字段业务不变量（例如 end_date 必须晚于 start_date、各分项金额之和必须等于 total_amount、或者抽出的实体必须真实存在于原文中）。因此生成端的约束解码永远不能替代后端的 stop_reason 检查与 Pydantic 业务语义校验。
  • 误区三：“为了让模型在输出 JSON 的同时保留推理过程，最佳实践是在 JSON Schema 的第一个字段硬编码一个 reasoning 或 thinking 字符串字段。” 事实：这曾是早期无原生思维链模型时代的常用技巧，但在新一代原生推理模型（如 DeepSeek-R1、Qwen3、Claude 4.6+/5.x 等）上已成为反模式——不仅把本该自由探索的思维过程锁死在 JSON 字符串转义规则内（模型每写一个换行或引号都要计算转义，增加算力与幻觉压力），部分闭源模型还会将 Schema 中的 reasoning/thinking 字段识别为思维链诱导抽取而直接触发 refusal 拒答。正确做法是让模型在独立的 <think> 或 Reasoning 通道中无约束思考，仅对最终输出块施加 Schema 约束，或仅保留简短的 explanation / evidence 审计摘要字段。

追问 01

为什么分词器的多字节 UTF-8 切分和 Token 边界对齐（Token Healing / Retokenization）会给约束解码带来麻烦？

展开追答：为什么分词器的多字节 UTF-8 切分和 Token 边界对齐（Token Healing / Retokenization）会给约束解码带来麻烦？
追答

在 GPT-4 / Llama-3 / Qwen 等广泛使用的 Byte-Level BPE 分词器（见 llm-0007）中，一个生僻汉字或 Emoji 的 3~4 个 UTF-8 字节可能被拆成两个独立的 Token。如果自动机建立在 Unicode 字符集上，遇到半个 UTF-8 字符的 Token 就会立即报错。XGrammar 因此将 PDA 直接建立在 原始字节（Byte，0x00–0xFF） 边上，天然支持跨 Token 拼接多字节字符。此外，在前跳解码（Jump-Forward）直接往上下文追加确定性字符串 s_det 时，字符串拼接可能改变原有的 BPE 合并边界（例如已生成 "http"，确定性追加 "://"，在标准 BPE 中 "://" 与前面的字符可能有不同的合并方式），因此引擎必须利用持久栈回退（Rollback）最近 1~2 个边界 Token 并对拼接后的文本重新分词（Retokenize），才能保证 KV Cache 与模型训练时的分词分布严格一致。

追问 02

直接把所有非法 Token 的 Logits 置为 $-\infty$ 并对剩余 Token 重新归一化，是否等于从真实后验条件分布 $P(\mathbf{y} \mid \mathbf{x}, \mathbf{y} \in L(G))$ 中无偏采样？

展开追答：直接把所有非法 Token 的 Logits 置为 $-\infty$ 并对剩余 Token 重新归一化，是否等于从真实后验条件分布 $P(\mathbf{y} \mid \mathbf{x}, \mathbf{y} \in L(G))$ 中无偏采样？
追答

不等价！这是一个在面试中极易答错的深度概率问题。约束解码在每一步做的是贪心局部重归一化（Myopic / Local Renormalization）： $$P_{\text{CD}}(y_t \mid y_{<t}) = \frac{m(y_{<t}, y_t) P_\theta(y_t \mid y_{<t})}{\sum_{y'} m(y_{<t}, y') P_\theta(y' \mid y_{<t})}$$ 而真实的全局条件分布由贝叶斯公式给出，要求乘上从状态 $y_{\le t}$ 出发未来所有步骤最终能生成完整合法序列的边缘概率（Future Grammaticality Probability） $\alpha(y_{\le t}) = \sum_{y_{>t}: y \in L(G)} P_\theta(y_{>t} \mid y_{\le t})$。局部掩码完全忽略了 $\alpha(y_{\le t})$，可能导致模型在某一步采样了一个当前语法合法、但后续无论怎么填都极违背模型语义常识的死胡同分支（Garden-Path Trap）。在关键高价值场景下，需要结合粒子滤波（SMC, Sequential Monte Carlo）或束搜索（Beam Search）来近似全局条件分布。

追问 03

当约束解码（如 XGrammar）与投机解码（Speculative Decoding）同时开启时，两者如何协同工作？

展开追答：当约束解码（如 XGrammar）与投机解码（Speculative Decoding）同时开启时，两者如何协同工作？
追答

如 llm-0006 所述，投机解码要求小模型（Draft Model）连续猜出 $\gamma$ 个候选 Token（或候选树），再由大模型（Target Model）一次前向并行验证。当叠加语法约束时：（1）Draft 模型在每一步生成草稿时同样挂载 PDA 状态机掩码，确保猜出的 $\gamma$ 个草稿 Token 100% 符合语法，避免浪费验证算力；（2）Target 模型在并行计算这 $\gamma$ 个位置的验证分布 $p(x)$ 时，利用每一步对应的自动机掩码同步屏蔽非法 logits；（3）一旦某个位置 $k \le \gamma$ 的草稿 Token 被拒绝，XGrammar 利用**持久执行栈（Persistent Execution Stack）**在 $\mathcal{O}(1)$ 时间内将自动机栈指针回滚（Rollback）到第 $k-1$ 步的状态，随后采样修正 Token 并继续推进。
