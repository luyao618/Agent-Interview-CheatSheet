## 问题

异步 Agent 的事件队列优先级，应该由规则还是 LLM 判断？请从语义紧急度、成本、延迟、可靠性等维度分析规则引擎、LLM 分类器与混合策略的取舍，并说明如何应对队列饥饿。

## 答案

> 🤖 AI 答案 · 模型：Claude-Opus-4.8 · 日期 2026-08-06

**核心结论：默认用规则，把 LLM 当兜底而非主判官。** 优先级判定处在事件入队的关键路径上，要求低延迟、低成本、可复现；这恰恰是规则的强项、LLM 的弱项。正确姿势是**分层混合**：规则先决大多数，语义模糊的少数才升级给 LLM。

**四个维度的取舍**

| 维度 | 规则引擎 | LLM 分类器 |
| --- | --- | --- |
| 语义紧急度 | 弱：只能看显式字段 | 强：理解「客户说要退款投诉」 |
| 成本 | 近乎零 | 每事件一次推理，量大即贵 |
| 延迟 | 微秒级 | 数百 ms，拖慢入队 |
| 可靠性 | 确定、可复现、可测 | 有波动、可能误判/被注入 |

规则赢在延迟、成本、可靠性，LLM 只在**语义紧急度**这一维度不可替代——所以让它只在需要语义理解时才出手。

**分层混合架构**

```
事件 ──► [L1 规则] ──命中──► 定级入队
           │ 未命中/模糊
           ▼
      [L2 LLM 分类] ──► 语义定级 ──► 缓存结果
           │ 超时/失败
           ▼
      [L3 兜底默认级] ──► 保证不丢
```

- **L1 规则**：来源、事件类型、SLA、显式关键词、付费等级等硬信号直接定级，覆盖 80%+ 流量。
- **L2 LLM**：仅对规则拿不准的自然语言事件做语义分级；结果按「事件指纹」缓存，避免重复付费。
- **L3 兜底**：LLM 超时或失败时落默认级并告警，**判优先级本身绝不能阻塞入队**。
- 关键工程点：LLM 判定**异步旁路、限时**，别放同步关键路径；给最高级设配额，防被恶意抬级刷穿。

**队列饥饿（低优先级永远排不上）**

纯优先级队列必然饿死尾部，务必叠加以下机制之一/多：

- **老化（aging）**：等待越久，有效优先级越高，超阈值强制提升；
- **加权公平调度（WFQ）**：按权重给各级配额，高优先不独占 100% 吞吐；
- **多队列 + 保底**：为低优先级预留最小 worker/带宽；
- **超时兜底 SLA**：任何事件超最大等待即强制出队。

**一句话**：规则做主、LLM 兜底语义、结果缓存、判定不阻塞入队，再用老化/加权防饥饿——这套组合在延迟、成本、可靠性与语义理解之间取得最佳平衡。

## 延伸 / 追问

**追问：什么信号说明该把某类事件从「规则」升级到「LLM 判定」？如何控制这部分成本？**

触发升级的信号有三类：① **规则置信度低**——命中多条冲突规则，或只落到「其它」兜底桶；② **纯自然语言载荷**——紧急度藏在用户措辞里（如工单正文「再不处理就退订」），无结构化字段可依；③ **误判代价高**——该类事件一旦压级会踩 SLA 或引发客诉。控成本四招：**(a) 缓存**，对语义等价事件按归一化指纹复用判定结果；**(b) 采样/降级**，高负载时对低风险事件退回规则、只对高价值租户走 LLM；**(c) 小模型**，分级是简单分类任务，用小模型或蒸馏分类器即可，不必上旗舰；**(d) 批处理**，把旁路的待判事件攒批一次推理，摊薄单条开销。核心原则：让 LLM 只处理「规则确实判不了、且判错代价高」的那一小撮事件。
