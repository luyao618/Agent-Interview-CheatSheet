## 问题

面对重度用户和不确定推理成本，AI 产品应如何设计订阅、按量与分层套餐？请为轻、中、重用户计算成本与套餐毛利，说明重试失败、重尾用量、配额、降档及透明计费的边界。

## 答案 · GPT-6

> 🤖 AI 答案 · 模型：GPT-6 · 日期 2026-09-17

**先把用户购买的价值单位、后台成本单位和双方承担的风险分开，再设计价格与限制。** 用户买的是完成任务或持续可用的能力，后台可能为一次任务调用多次模型、工具和检索。订阅收入固定而成本可随使用增长；按量能把部分风险与收入关联，却增加账单不确定性；分层可以匹配不同需求，但不能靠隐瞒配额、偷偷换差模型或虚构高价套餐来维持利润。

质量/成本/业务指标见 [product-0003](product-0003-ai-product-metrics.md)，供应商调用账单的归集与对账见 [engineering-0016](engineering-0016-llm-billing-reconciliation.md)。本题的增量是可计算的定价与成本责任，不把后台每次收费直接变成对用户多收一次。

### 1. 定价单位先承诺什么，再选择收入结构

先定义“一次任务”：覆盖哪些输入规模、工具、输出长度、质量与超时边界，什么状态算成功交付，取消/失败/部分交付怎样计费。若任务成本差异过大，可以按任务类型、明确的模型档位或加权 credits 计量，但必须让用户在执行前知道换算规则；一条消息不能无限承载长文、多轮 Agent 与昂贵工具。

| 方案 | 适用条件与用户价值 | 代价及不适用场景 |
| --- | --- | --- |
| 固定订阅 | 高频稳定需求，用户重视可预测支出 | 收入不随任务量增长；未经成本边界验证的“无限量高质量”不适合重尾或开放式 Agent |
| 按量 | 偶发使用、工作量可计量，用户愿意控制预算 | 账单波动，低用量时固定支持/收款成本占比高；不适合完全看不懂计费单位的用户 |
| 分层订阅加包含量/超额价 | 不同使用强度能得到真实差异，如包含量、并发、SLA或超额费率 | 增加选购与迁移复杂度；必须保证每档有真实用途，不能造一个被完全支配的“贵套餐”只当锚点 |

**套餐分层不等于阶梯计费算法。** Basic/Pro 是不同承诺；volume pricing 与 graduated pricing 则涉及全量或分段怎么定价。本文超额价只作用于超出包含量的部分，不会跨过阈值后给所有历史任务重新定价。也不能把聊天会员价格当作 API 使用成本或默认包含 API 额度。

Stripe 一手文档区分 flat rate、usage-based、fixed fee and overage 等模式；固定作者示例将 meter、price、subscription 与 meter event 分开建模，见 `usage-based-subscriptions/server/python/server.py:64–146`。它说明计量与商品/订阅是不同对象，**不证明本文的利润、配额保护或退款政策由该示例实现**；这里没有执行作者代码或创建任何对象。

### 2. 一组完全合成的成本假设

以下数值全部为 **2026-09-17 编写的虚构 USD / 月、不含税教学假设**，包括套餐价、模型成本与收款费；不是 Stripe、模型供应商或本项目的真实报价。月收入按本月已提供服务的净收入建模；暂不含退款、折扣、期中变更、坏账、汇率、融资与所得税，遇到这些项目须再调整，不能把预收现金直接当利润。

- 每次模型尝试成本 p=0.02 USD，每个发起任务另有工具/编排直接成本 a=0.0035 USD；尝试即产生成本，包含失败尝试，本例不设供应商退款。
- 25% 的首尝失败并最多自动重试一次，重试恢复率 80%。所以平均每发起任务 1.25 次尝试，最终成功率 s=1−0.25×(1−0.80)=0.95；用户仅对成功交付计量，失败/交付前取消不消耗付费成功额度。
- 每发起任务期望成本为 0.02×1.25+0.0035=0.0285 USD；长期按成功交付分摊的期望成本 c=0.0285/0.95=**0.03 USD/成功任务**。它不是每个任务的实测成本，也不是成功率保证。不同任务混合、不同重试价格或失败相关性须另建模型。
- 每活跃账户每月直接服务成本 A=1 USD；有正数月账单时，虚构收款成本为月收入的 f=3% 加 b=0.30 USD。这些是本题指定的直接 COGS 分类，不是财务准则或真实收单收费。每月一张汇总账单，计算保留精度，展示时按 HALF_UP 到分；不先把每次小额成本四舍五入。

三层口径必须分开：**任务层毛利**先看可归属收入减履约成本，例如按量价 0.12 下为 0.12−0.03=0.09 USD/成功任务，尚未分摊月成本和收款费；订阅的固定费没有天然的单任务售价，若用 P/q 分摊收入必须说明 q。**套餐/月账户毛利**为 GP=P(q)−[c×q+A+f×P(q)+b]，毛利率 G=GP/P(q)；P=0 时不收本例账单手续费且毛利率无定义，账户成本仍可能存在。**整体经营利润**再用所有账户毛利之和减研发、营销和管理等期间费用；它仍不是扣完融资和税费后的净利润。

### 3. 给轻、中、重用户算一遍，再设计用量边界

候选方案均为虚构：按量 **0.12 USD/成功任务**；标准档 **20 USD/月含200次，超额0.12**；专业档 **60 USD/月含600次，超额0.09**。两档包含量本月有效、不结转；超额默认关闭，只有用户同意价格版本与月预算后才开启。以下只比较同质量任务，不能用隐藏模型降档换出低成本。

本例轻/中/重用户每月成功任务 q=50/400/3,000，按满足相同需求的最低报价选择。中用户标准档 44 USD=20+200×0.12；重用户专业档 276 USD=60+2,400×0.09。**后两种都假定已经明确开启超额**，月预算分别为50/300 USD；默认不允许悄悄跑出这张账单。

| 用户/月成功量 | 期望履约成本 c×q | 所选方案/月收入 | 月账户毛利 | 月毛利率 | 若20 USD不限量：月毛利 |
| --- | --- | --- | --- | --- | --- |
| 轻 / 50 | 1.50 USD | 按量 / 6.00 USD | 3.02 USD | 50.33% | 16.60 USD |
| 中 / 400 | 12.00 USD | 标准+超额 / 44.00 USD | 29.38 USD | 66.77% | 6.10 USD |
| 重 / 3,000 | 90.00 USD | 专业+超额 / 276.00 USD | 176.42 USD | 63.92% | -71.90 USD |

轻用户按量毛利率只有50.33%，低于下面的60%套餐设计目标；可以接受这部分获客成本、降低直接支持成本，或在选购前明示最低消费方案，不能事后暗加费用。三档各自在轻/中/重需求下有价格用途；但最低报价不代表用户一定愿意购买，功能价值、留存与真实支付意愿还需独立验证。

若暂定包含量用满时目标毛利率 g=60%，在上述成本分类下可规划：**q≤floor([P×(1−f−g)−A−b]/c)**。标准/专业档上限分别为203/696个成功任务，故示例选200/600；这是依赖期望成本的规划界，不是每个账户的利润保证。20 USD 不限量方案的盈亏平衡约603次，不能把这个“零毛利上限”误当60%毛利配额。

超额部分要达到同样的增量毛利目标，至少需 p_extra≥c/(1−f−g)=0.081081… USD/成功任务，向上取到分为0.09；它未分摊固定成本，也不自动保证整个套餐毛利。费率或支持成本变化都要重新算。真实产品还需设置输入/输出长度、工具预算、并发和每任务最多尝试次数；只限成功数，仍可能被大量不收费的失败任务拖垮。

### 4. 平均成本不能代替重尾与敏感性分析

合成基线有1,000名用户：800轻、180中、20重；总计172,000次成功任务，均值172次，但 **2%的重用户贡献34.88%的用量**。这是人为离散长尾场景，用来暴露风险，不是假称已从真实数据拟合 Pareto 分布。上线前应按任务类型、用户分位、重用户迁移和成本尾部看分布；均值能用于总额核算，却会掩盖哪些人亏损、哪种承诺会吸引更多重用户。

保持总人数不变，把重用户从20增到100、轻用户降为720，中用户仍180，则总任务变为408,000。不限量方案收入仍为20,000 USD，基线成本下其毛利率从64.70%降到29.30%。分层方案只在使用者实际接受更高报价并付款时才增加收入；本模型没有测价格弹性或流失，不能据此证明它必胜。

进一步独立改变每次尝试成本与失败恢复，再算联合压力；下表每行都实际执行了 Decimal 复算，但数字来源仍是合成假设。

| 情景：尝试USD；首败/重试恢复率 | 期望成功任务成本 USD | 标准/专业60%目标规划上限 | 超额价向上取分下界 USD |
| --- | --- | --- | --- |
| 基线：0.02；25%/80% | 0.030000 | 203 / 696 | 0.09 |
| 尝试成本翻倍：0.04；25%/80% | 0.056316 | 108 / 371 | 0.16 |
| 重试恶化：0.02；40%/50% | 0.039375 | 154 / 530 | 0.11 |
| 联合压力：0.04；40%/50% | 0.074375 | 82 / 281 | 0.21 |

原来标准/专业的200/600额度，在联合压力下超过82/281的规划上限，超额0.09也远低于新的0.21规划价格。应先看成本/质量修复、风险预算与未来新版本套餐；**不能给现有用户偷偷减额度、补收差价或降低质量**。若成本失控需要临时暂停，解释服务故障、剩余额度与补偿/展期/退款规则，而不是把服务方失败伪装成用户超额。

整体利润也要单列。合成基线按量/分层组合月收入18,240 USD、直接COGS 7,007.20、毛利11,232.80（61.58%）；再扣本例研发/营销/管理期间费用12,000，**经营利润为−767.20 USD**。有毛利并不等于公司盈利。联合压力加重用户占比上升时，组合毛利率降到17.57%，经营利润−5,000.20；这不是预计收入或真实亏损报告。

### 5. 把配额、成本责任和支付体验写成透明契约

- **选购前**：展示币种、税费是否另计、周期与重置时区、包含量、计费成功条件、超额单价、总额上限、额度结转规则和续费/取消/退款方式。专业档的真实权益/费率差异要说得清楚，不能默认勾选高价档或用虚构原价制造折扣。
- **执行前**：同时看已成功量与在途预留，显示本次预计计量、剩余额度和预计月总额。标准档已成功199、在途1时再发1次已超出200；不能只看199就放行。价格版本改变要重新报价；跨月预留与迟到结算须绑定原计量周期，不能靠本地时间猜归属。
- **临近/达到限制**：例如80%提示，100%时按已公布规则等待重置、明确升级、开启带预算的超额，或另选经济档。经济档必须告知模型/质量/能力变化并取得新条款同意、通过独立质量验收；提示词里写“不能降档”不是权限或质量保证。
- **服务侧风险**：用户账单上限和供应商成本预算是两个账本。若已消耗6.07 USD、在途预留0.04、下个任务上界0.0435，而预算6.10，应暂停接受新任务；已付额度如何保留/补偿需明示。成本未知则先核对。上界成立还依赖实际限制模型/工具/重试，不能由 UI 上的余额数字保证。
- **结算与付款后**：用户能核对成功任务数、单价版本、周期、超额和调整项，能查询争议、下载明细并清楚取消续费。付款失败、取消和退款要有可理解的状态与宽限/恢复规则；不能既重复扣款又让用户看不见处理进度。后台失败/重试成本保留，但不自动多扣成功额度。

Stripe 当前记录用量文档说明 meter events 异步处理，摘要/即将出具的发票可能暂未反映新事件，并要求考虑事件 idempotency。因此“调用计量接口成功”不等于已结算余额，更不提供本地实时限额的原子保证。真实系统仍需服务端可信计量、预留/提交/释放、去重、价格生效版本及对账；本题没有实现支付网关或验证任何真实账单。

### 6. 原创计算与失败边界验证

离线 Python 程序使用 Decimal，部分成本公式还用 Fraction 独立复算。原始假设、12个用户/方案格、4组成本×4组群体/方案结果、6个用户门禁和3个服务成本判断均随证据包保存。26项测试覆盖期望成本、零收入、配额取整、负数/bool/NaN拒绝、价格阈值、方案选择、重尾、期末舍入、重复最终记录、未知结算和在途预留。

另有四个原创任务的最终记录：成功的两项分别尝试1/2次，失败一项尝试2次，取消一项尝试1次，另重复传入第一项同一记录。应去重为4任务、6次尝试，直接成本 **6×0.02+4×0.0035=0.134 USD**，对用户只计2次成功。它与期望分摊0.03并不相同，正好说明小样本和失败组合会偏离规划均值；待定记录或相同ID的冲突最终状态不能按零补齐。

同一组三条断言对“丢弃失败成本”与“忽略在途额度”的错误候选，分别真实 exit1 / 1 failure / 0 errors；修正版 exit0 / 3 pass。完整26项和所有合成计算通过，独立临时副本也复跑；输入字节未改，临时目录已清理。这里验证的是算术和给定快照决策，**不是并发CAS、身份认证、实时扣款、退款、付款UI或商业收益**。所有计费接口/模型调用/生产发布均 not_run，production_approved=false。

## 延伸 / 追问

- **用户开始集中使用昂贵任务，还能按“任务数”收费吗？** 先检查任务单位是否仍可比；必要时公开不同任务/模型的权重和限制，执行前估价。要同步质量要求、成本分布和套餐版本，不能把后台重试私自换成用户多次任务。
- **失败不扣用户额度，怎样避免无上限成本？** 每任务有尝试/工具上限，服务侧另设消耗与在途成本预算，未知用量先核对；超线透明暂停并处理补偿。成功配额和账单封顶都不能代替这些保护。
- **套餐毛利不错，为什么现金仍紧张？** 期间费用、获客回收期、退款与付款时点都会影响；年付预收、按月收入确认和供应商付款也可能错期。本题仅算简化月经营利润，不能从毛利率推出净利润或现金流。

## 常见误区

- **“平均用户便宜，开无限量就安全。”** 重尾、昂贵任务混合、逆向选择和失败成本都可能改变均值；应做分层与联合压力分析。
- **“隐藏降档或放个没人该买的高价档，就能提高利润。”** 这破坏质量承诺与知情选择；档位必须有真实差异、清楚计量和可撤回的选择。
- **“任务毛利、套餐毛利、整体利润是一回事。”** 固定服务成本、收款费和期间费用归属不同；不说明分摊与分母就无法比较。
- **“示例费率是现价，mock 通过就能收费。”** 本文价格全部虚构；上线需核对实际合同、币种/税费/日期、付款与退款链路，并独立验证用户接受程度。
