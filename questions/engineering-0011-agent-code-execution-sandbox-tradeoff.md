## 问题

Coding Agent 会自己生成代码并执行（跑脚本、装依赖、调 API）。沙盒锁得太死，Agent 干不了活（装不了包、连不了网、读不到数据）；开得太松，恶意/失控代码就能逃逸、外传数据、打穿宿主。如何在沙盒安全与能力开放之间取平衡？

## 答案

> 🤖 AI 答案 · 模型：Claude-Opus-4.8 · 回答 2026-08-06

**先立原则：默认全关 + 按需授权（deny-by-default, capability on demand）。** 别追求一个"既安全又全能"的静态配置——那不存在。正确姿势是给一个**强隔离的最小沙盒**打底，再按任务**按需、临时、可审计地**放开具体能力。安全是基线，能力是增量，而非反过来。

```
        能力开放 ──►
安全 ▲  ┌───────────────────────────────┐
     │  │ 强隔离沙盒（默认无网/只读/限额）│ ← 基线
     │  │   +按需网络白名单              │
     │  │   +按需可写目录                │ ← 任务级临时授权
     │  │   +按需依赖（预置/私有镜像）    │
     │  └───────────────────────────────┘
     │   逃逸风险随开放度上升 → 靠隔离强度兜底
```

**五个维度分别怎么权衡：**

1. **隔离强度（地基）。** 用容器 + 用户态内核（gVisor）/ microVM（Firecracker）而非裸容器，一次一任务、跑完即销毁的**一次性环境**。开放度越高，越要靠强隔离兜住逃逸——地基决定了你敢开多松。

2. **网络。** 默认**无网**。需要时给**出站白名单**（只放特定域名/私有 API），禁内网元数据端点（如 `169.254.169.254`，防偷云凭证）。别给全网出站——数据外传和拉恶意载荷都走这里。

3. **文件 / 系统调用。** 根文件系统只读，只挂一个临时可写工作目录；用 seccomp 收窄 syscall。数据隔离：只挂本任务所需数据，绝不挂宿主敏感路径与共享凭证。

4. **依赖安装。** 别开公网 `pip/npm install`（供应链投毒面大）。走**私有镜像源 + 预置常用包 + 锁 lockfile**，需要新包时审核加入白名单。

5. **资源限额 + 审计。** CPU/内存/磁盘/时长硬上限（防挖矿、fork 炸弹、死循环）；全程记录执行了什么代码、访问了什么、产出什么，异常行为告警。审计让"开放"可回溯、可追责。

**渐进授权（把静态难题变成动态流程）：** 低风险动作（纯计算、读己数据）自动放行；要联网、要写外部、要装新包这类高风险能力，走**升级授权**——命中策略引擎则临时授予、必要时人工审批，用完即收。这样把"一次性配死"变成"按任务最小授权"。

**一句话：** 别在"锁死"和"全开"之间找一个中间点，而是**强隔离打底 + 默认全关 + 按需临时授权 + 全程审计**——安全是不可协商的基线，能力按任务增量放开、用完即收，逃逸风险始终由隔离强度兜底。

## 延伸 / 追问

**追问：Agent 生成的代码本身可能被 prompt injection 诱导写出恶意逻辑（外传数据、扫内网），沙盒之外还该防什么？**

沙盒是"就算代码是恶意的也跑不出去"的最后一道墙，但不能只靠它。还要在**沙盒之外**加纵深防御：① **可信边界**——把不可信输入（RAG 检索到的网页、用户上传、上一步工具结果）与执行意图隔离，注入进来的"指令"不该直接变成放开能力的依据；能力升级的决策权在 harness/policy，不在被注入的模型自述。② **出口管控**——即便沙盒放了网，也在出口做 DLP：限制可外传的数据量与目的地，敏感数据（密钥、PII）打标后禁止出网，堵住"扫内网/外传"的最后一公里。③ **能力申请可审计 + 人在环**——高风险能力（联网、写外部、装包）的申请要显式、可解释、留痕，异常模式（突然要连陌生域名）触发人工确认。④ **最小权限的凭证**——沙盒里即便拿到 token 也是短时、窄 scope 的委托令牌，泄露损失有限。核心：**假设模型可能被操纵**，用"隔离 + 出口管控 + 能力审批 + 最小凭证"多层兜底，而不是指望模型永远不被注入。
