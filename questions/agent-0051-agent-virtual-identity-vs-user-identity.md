## 问题

Agent 替用户对外办事（订机票、发邮件、调第三方 API、跟另一个系统交互）时，应该用一个专属的虚拟身份（agent 自己的账号/凭证），还是直接用用户本人身份（冒用户之名）？各自的信任、权限、审计、可撤销性、第三方接受度如何权衡？

## 答案

> 🤖 AI 答案 · 模型：Claude-Opus-4.8 · 回答 2026-08-06

**先破"二选一"：真正该问的是"如何表达委托"。** 现代做法不是"agent 冒充用户"，而是**用户授权一个可识别的 agent 身份，代表用户在受限范围内行动**——即 OAuth 式的**委托授权 / on-behalf-of**：身份是 agent 的（可审计、可撤销），权限是用户授予的子集（最小、有范围、可过期）。"纯用户身份"和"完全独立虚拟身份"是这条谱系的两端。

```
      纯用户身份            委托身份(推荐)           完全独立虚拟身份
  agent 用用户凭证    agent 自有身份+用户授权 scope   agent 自有账号与权限
  ├ 第三方无缝接受    ├ 可识别"这是 agent 代办"       ├ 与用户解耦、可独立管控
  ├ 无法区分谁做的    ├ 审计到具体 agent+委托链       ├ 第三方可能不认/需单独授权
  └ 撤销=改密、粗暴   └ 撤销=收回该 token，精准        └ 需自建信任与合规
```

**四个维度的权衡：**

1. **信任 / 第三方接受度。** 纯用户身份对第三方"透明"、无需改造，但对方无从知道是人还是 agent 在操作，出问题难追责。委托/虚拟身份需要第三方支持 OAuth scope 或识别 agent，接受度取决于生态成熟度——正因如此，很多场景现实里仍走用户身份 + 前置授权。

2. **权限（最小化）。** 用户身份 = agent 继承用户**全部**权限，越权风险最大。委托身份只拿**完成任务所需的最小 scope**，天然限爆炸半径——这是安全上偏好委托的核心理由。

3. **审计。** 用户身份下，日志只显示"用户做的"，人和 agent 的行为混在一起、无法归因。独立/委托身份让每个动作可追溯到"哪个 agent、依据哪次授权、代表哪个用户"，责任链清晰。

4. **可撤销性。** 用户身份要停 agent 只能改密码（连人一起断）。委托 token 可**单独吊销、设过期、限速率/额度**，精准且不影响用户本人——运维与止损上远优。

**选型建议：** 有标准委托授权可用（OAuth on-behalf-of、服务账号 + 范围令牌）→ 优先**委托身份**，享最小权限 + 可审计 + 可撤销。第三方只认用户、无法改造 → 退回**用户身份**，但必须补偿：前置显式授权、动作确认、独立审计标记"由 agent 代办"、可快速吊销的凭证。跨组织、需长期独立运营的 agent（如做市/爬取/对账机器人）→ 给**独立虚拟身份**并单独合规。

**一句话：** 默认走"**agent 可识别身份 + 用户委托的最小可撤销权限**"，而不是让 agent 顶着用户的名字拿全部权限裸奔；只有第三方无法支持委托时，才退回用户身份并叠加授权、审计、可撤销的补偿措施。

## 延伸 / 追问

**追问：既然委托身份更安全，为什么现实里很多 agent 还是直接用用户身份？**

因为**委托授权依赖对端支持，而多数系统还没准备好**。用委托/独立身份的前提是第三方能识别并接受"一个非用户主体代表用户"——需要它实现 OAuth scope、服务账号、或 agent 白名单。现实是大量遗留系统、内部工具、传统网站只有"用户名密码/用户 session"这一种入口，压根没有"代理身份"的概念；agent 要办成事，只能拿用户凭证去登。其次是**成本与体验**：搭一套委托授权、凭证托管、scope 管理是实打实的工程投入，早期产品往往先用用户身份跑通，再谈治理。还有**信任惯性**——很多第三方对"机器人代办"直接风控拦截（反爬、反自动化），反而逼 agent 伪装成用户。所以这不是"用户身份更好"，而是"委托身份的基础设施还没铺开"。合理路径是：能用委托就用委托；被迫用用户身份时，用凭证隔离（专用受限子账号）、最小授权、动作审批、行为审计与快速吊销把风险压到可接受，并推动对端支持标准化的 agent 委托。
