## 问题

LLM 应用开发为什么不能仅调用大模型 API，会遇到哪些问题？

## 答案 · Claude-Opus-4.8

> 🤖 AI 答案 · 模型：Claude-Opus-4.8 · 回答 2026-07-12

**本质**：大模型 API 只是一个**无状态、单轮、纯文本进出**的原子能力——给一段 prompt，返回一段生成。而「应用」要在真实业务里稳定、准确、可控地解决问题，中间隔着一整层工程。裸调 API 相当于只拿到 CPU 指令，却还没有操作系统。

```
  裸 API：  prompt ──► [LLM] ──► text
                       （无记忆·无外部数据·不能执行·不保证格式）

  应用层： 输入 ─► 记忆/会话 ─► 检索(RAG) ─► 编排/工具调用 ─► LLM
                                  ▲                          │
                                  └──── 校验·护栏·重试 ◄──────┘
                     全程叠加：缓存 · 限流 · 观测 · 评测 · 安全
```

**仅调 API 会撞到的问题（按层）**

**1. 知识与准确性**
- **知识边界 & 幻觉**：模型只有训练截止前的通用知识，不懂你的私有/实时数据，且会一本正经编造 → 需 **RAG**（检索注入事实 + 引用溯源）。
- **上下文窗口有限**：长文档、长对话塞不下，且越长越贵越慢、易「lost in the middle」→ 需检索、摘要压缩、记忆管理。

**2. 能力与交互**
- **无记忆/无状态**：每次调用独立，不记得上一轮 → 需自建会话状态与短/长期记忆。
- **不能触达外部世界**：只会生成文本，不能查库、调接口、算数、发邮件 → 需 **function calling / 工具调用**。
- **单步、无编排**：复杂任务要拆解、多步推理、循环、条件分支 → 需 **Agent / workflow 编排**。
- **输出不可靠**：格式漂移、不保证合法 JSON、字段缺失 → 需结构化输出约束 + 校验 + 重试兜底。

**3. 工程非功能性（最容易被低估）**
- **成本/延迟/稳定性**：token 计费、限流(429)、超时、偶发抖动 → 需缓存、并发控制、重试退避、降级。
- **可观测性**：调用链、token、命中率、失败率不埋点就是黑盒 → 需日志 / trace。
- **质量保障**：prompt 一改就回归 → 需评测集 + 回归，用数据驱动而非拍脑袋。
- **安全合规**：prompt 注入、越权工具调用、敏感数据泄露、有害输出 → 需 guardrails、权限隔离、脱敏、审计。

**一句话**：API 提供的是「生成」这一原子能力；把它变成可用的产品，缺的是**事实（RAG）+ 行动（工具）+ 编排（Agent）+ 工程（成本/观测/评测/安全）**。这几层正是 LLM 应用工程的主战场。

> **要点**
> - LLM API = 无状态·单轮·纯文本的原子能力，不等于应用
> - 准确性：知识边界 + 幻觉 + 上下文限制 → RAG / 记忆
> - 能力：无记忆、不能执行动作、无编排、输出不可靠 → 工具调用 / Agent / 结构化输出
> - 工程：成本、延迟、限流、观测、评测、安全一个都不能少

## 延伸 / 追问

**追问：那是不是所有 LLM 需求都得上 RAG + Agent 这套重型架构？**

不是，要按需分层、避免过度工程。判断标准是任务的**三个维度**：是否依赖私有/实时知识（否则不需要 RAG）、是否需要执行外部动作（否则不需要工具）、是否多步且状态复杂（否则不需要 Agent 编排）。

- **纯生成类**（润色、翻译、分类、摘要固定文本）：一次 API 调用 + 输出校验即可，别硬塞检索。
- **问答/知识类**：加 RAG 保证事实与溯源，通常还不需要 Agent。
- **任务执行类**（查数据、下单、跨系统操作）：才需要工具调用乃至多步 Agent。

原则：**从最简方案起步，被真实痛点（幻觉、做不了动作、单步不够）推着逐层加**。哪怕最简单的场景，成本、限流、观测、安全这几项工程护栏也几乎总要保留——它们与架构复杂度无关，是上线的底线。
