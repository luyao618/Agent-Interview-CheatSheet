## 问题

AI 生成的代码功能正确但数据量一大就变慢，如何验收复杂度并选择更合适的数据结构？请比较五十万条记录的双循环与哈希去重，并分析百万条记录取 Top-10；说明语义、时间/空间、最坏边界与有界实测如何相互校验。

**先固定“结果相同”的含义，再证明工作量如何增长，最后用有资源上限的实验检查实现。** 小样本功能测试通过，只说明这些输入得到预期结果；AI 写出的嵌套扫描、重复排序或隐藏复制，仍可能在大规模时不可用。复杂度分析负责解释增长率，计时和内存记录负责暴露常数、分布与实现成本，两者都不能独自证明生产容量。

峰值系统筹备见 [engineering-0008](engineering-0008-peak-qps-system-design.md)，执行后验证见 [engineering-0010](engineering-0010-execute-verify-feedback-loop.md)。本题聚焦单进程算法的验收，不以本机合成数据代替业务服务压测。

### 1. 先建立可比较的语义和成本模型

本例记录是不可变三元组 `(key, score, ordinal)`，`ordinal` 是原始输入的连续序号。边界校验要求三个字段是整数、key 非负，排除 bool、NaN 和缺失字段；实测常规 key/score 较短，另设较宽整数的碰撞数据。算法内核接受已经校验的数据，不是对任意对象开放的接口。

- **去重**：按 key 相等判重，保留第一次出现的整条记录，并保持首次出现的顺序。不能悄悄改成“最后一条覆盖”、只返回 key 集合，或按 key 重排结果。
- **Top-10**：取 score 最大的至多十条记录，score 并列时较早输入者优先；同 key 的不同记录仍参与竞争。这不是“出现次数最多的十个 key”，也没有先去重。若需求是那两种语义，需要另写聚合或去重阶段。
- **成本模型**：令 n 为记录数、u 为不同 key 数、k 为保留条数。下表先把一次 key 的哈希/比较视作 O(1)，并统计除输入外的辅助结构和输出。长字符串、自定义比较器、大整数的位数增长，会增加每次操作的成本；不能只数循环层数。

| 方案及相同语义的补足 | 时间边界 | 额外空间 | 适用与代价 |
| --- | --- | --- | --- |
| 双循环：对已保留记录逐个比较，遇重复即停 | O(nu)，全异时 Θ(n²)；全同且比较有界时 Θ(n) | O(u)，主要是输出 | 简单、可作小规模参照；不适合大量不同 key |
| 哈希集合查重，同时追加首次记录 | 良好散列下期望且均摊 O(n)；大量碰撞可退化为 O(n²) | O(u)，集合与输出 | 一遍处理、保序方便；付出哈希表内存，不能给任意输入恒定延迟承诺 |
| 稳定按 key 排序，相邻去重，再按 ordinal 恢复顺序 | 最坏 O(n log n + u log u)，简写 O(n log n) | 本 Python 实现 O(n)，含复制、排序临时空间和输出 | 不依赖哈希分布；多一次恢复顺序，不能把它说成原地 O(1) 空间 |
| 全排序，按 `(-score, ordinal)` 取前 k | 最坏 O(n log n)；有序结构可让自适应排序少做工作 | 本 Python 实现 O(n) | 需要完整排名或 k 接近 n 时合理；只要少量结果时可能浪费内存 |
| 有界堆，只保留当前最好的 k 条，最后排好这 k 条 | 1 < k < n 时 O(n log k + k log k) 上界；先建堆 O(k)，每条至少判一次是否更好 | O(k) | 小 k 或流式输入合适；不是“所有输入都会优于排序” |

**平均与均摊是两件事。** 平均/期望依赖输入或散列分布；均摊是把一串操作的总成本分到各次操作。普通扩容可能要搬移/重新插入已有元素，良好散列和几何增长才支持常见的均摊分析；它不会消除某次扩容的延迟，也不会修复恶意碰撞。单次碰撞查找可能扫描许多槽位；碰撞下重建的成本也不能套用普通输入的估计。

固定 CPython 3.11.8 的 `Objects/setobject.c:56–99` 有探测循环和相等比较，`:175–177` 会触发扩容，证明实际实现并非“一次哈希就完事”。`Lib/heapq.py:463–521` 的 `nsmallest` 对 k=1 用 min、k≥输入长度时改用 sorted；一般路径维护最大堆、只替换更好的项，再排序保留结果。这里的 k 对应库参数 n，不能混淆。源码注释的作者实验数字也不是本文实测。

### 2. 五十万条去重：先守住首次记录，再看增长

下面是本题原创内核摘录；输入生成、字段校验、结果校验、文件输出都在计时区间外。二重循环只扫描已保留的记录，哈希版本用独立列表保序，而不依赖 set 的遍历顺序。

```python
def dedup_nested(records):
    out = []
    for r in records:
        for old in out:
            if r[0] == old[0]:
                break
        else:
            out.append(r)
    return out


def dedup_hash(records):
    seen, out = set(), []
    for r in records:
        if r[0] not in seen:
            seen.add(r[0])
            out.append(r)
    return out
```

例如输入 `[(9,1,0), (2,2,1), (9,99,2)]`，正确输出是前两条；用 dict 推导式覆盖相同 key 会把最后的 score=99 留下，虽然速度快，仍不符合契约。排序版必须稳定保留组内第一条，再恢复 ordinal 顺序，否则也不可与前两种比较。

对于 **500,000 条全异记录**，该双循环需要 `n(n−1)/2 = 124,999,750,000` 次 key 相等比较。这是理论精确计数，**未执行五十万条双循环，也没有外推秒数**。在 1,000 / 2,000 / 4,000 条全异输入上，另一次带计数器的有界运行分别得到 499,500 / 1,999,000 / 7,998,000 次比较；未把计数器开销混进下面的计时。

同三档规模的双循环中位耗时为 3.872 / 16.199 / 67.139 ms，哈希为 0.028 / 0.056 / 0.107 ms。增长趋势与分析一致，但三个点不能证明任意规模都服从同一常数。哈希版对每条做一次成员检查、对首次 key 再插入；这些是 API 操作数量，不是实际探测槽位次数。重复越多，u 越小，双循环和哈希的成本都会变化。

### 3. 百万记录 Top-10：相同排序键，保留不同的工作量

本例全排序调用 `sorted(records, key=lambda r: (-r[1], r[2]))[:10]`；堆调用 `heapq.nsmallest(10, records, key=lambda r: (-r[1], r[2]))`。负 score 把“最大分数”转换为最小排序键；ordinal 明确并列规则。堆顶是当前保留项中最差的排序键，新项更好才替换，因此只保留 k 个候选，但仍必须读完 n 条才能得到精确结果。

百万条、k=10 的理论工作量比较是 O(n log n) 与 O(n log 10)，不是两个已知秒数。k 是变量时还要计最终 O(k log k) 排序；k 固定为 10 时堆算法随 n 线性增长。k=0、n<k、负 k 要有接口约定；本例前两者分别返回空和所有已排序记录，负数及 bool k 被拒绝。

独立的结果检查验证输出长度、对象来自原输入、严格排序、没有漏掉比最差入选项更好的记录；小规模穷举还用人工规则的分数桶作参照。十二条同分记录必须返回原输入最早的十条；把 `(score, ordinal)` 整体降序会优先保留较晚记录，是一个真实可检出的教学反例。

### 4. 有界实测：数字与边界一起交付

下列是 **2026-09-17（Asia/Shanghai）本机真实运行**，不是课程曲线或模型生成的预测：Apple M5 Max、48 GiB RAM、macOS 26.6.2 arm64，CPython 3.11.8 `chromium.35` / Clang 13.0.0。固定 PRNG seed=409；同一分布的候选使用相同输入 SHA256。常规去重为打乱的全异 key、每 key 恰好五次的打乱数据，以及全同 key；Top-10 为整数随机分数 0…1,000,000、循环 0…16 的大量并列、严格递增分数。

每格独立子进程，**一次预热、三次未开启 tracemalloc 的内核计时、一次单独内存采样**；计时用 `perf_counter_ns`，内核执行时关闭循环 GC、完成后恢复。没有随机化候选执行顺序或控制温度/其他进程；中位数和范围只描述这三次观察，不是置信区间或 p99。官方 timeit 文档强调查看完整向量与最小值，本例一并保留原值，未把中位数冒充唯一正确统计量。

额外 traced peak 从输入已构造之后开启 tracemalloc，**含本次输出和算法临时分配，不含既有输入**；MiB=2²⁰ bytes。堆的 2,460 B 不代表百万记录只占这点内存：本次先物化整个输入，并非流式读取。另记 `ru_maxrss` 的整进程生命周期峰值，含解释器、输入、校验、预热及内存采样，不能与 traced peak 相减当成精确输入大小；本矩阵最大为 529.34 MiB。tracemalloc 不是所有本地分配或系统内存的完整账本。

两个反直觉结果需要保留：递增 score 让新记录反复替换堆顶，而自适应排序识别出已有顺序，所以这里全排序比小堆快；50 万全异去重的排序版额外 traced peak 又低于哈希版。它们支持按分布和预算选择，不能证明排序或堆的普遍优劣。

碰撞实验另用 `key=i*sys.hash_info.modulus`，在本机 P=2,305,843,009,213,693,951 下验证所有 key 的 hash 都为 0，同时值互不相同。1,000 / 2,000 条的哈希去重中位数为 5.033 / 19.250 ms，结果仍正确。键比常规 key 更宽，时间差不是对“纯碰撞代价”的单因素估计；明确碰撞已发生及其退化趋势，不能推成网络服务攻击吞吐或所有语言的行为。自定义对象还需满足相等与 hash 一致、key 不可变；不满足时先修语义，不谈性能优化。

资源规则为顺序执行、最多百万记录、二重循环最多 4,000、碰撞最多 2,000；每子进程 wall timeout 30 秒、CPU 软/硬限制 20/21 秒，整轮预算 240 秒，首个错误/超时即停止并保留输出。RSS≤1 GiB 是运行后的验收检查，**不是 OS 硬内存隔离**。本次 19 格完成、子进程均收集、专属临时目录已回收；另用一个自有休眠子进程验证超时后终止和回收，未压测业务服务。

交付包保存生成器、输入/输出指纹、三次原值、内存口径、命令和 stderr。16 项测试含重复、碰撞、并列截断、空集、k 边界、无输入修改及小规模穷举；同一组三条断言对“最后覆盖”与“较晚并列优先”错误候选分别真实 exit1 / 1 failure / 0 errors，对修正版 exit0 / 3 pass。两次红灯属于刻意构造的候选语义错误，不冒充生产事故；runner 超时探针也不计为算法失败。复跑命令为 `python3 -m unittest discover -s . -p test_algorithms.py -v`、`python3 probe_semantics.py fixed`、`python3 benchmark.py --output fresh-measurements`，输出目录必须不存在；`--small` 仅跑有界小规模子集，不能冒充百万规模复跑。

### 5. 把结果转成验收条件

提交优化时交代语义断言、成本推导、输入分布、规模、原始测量和停止条件，再由业务方给出预算，例如目标规模下内存上限、端到端 p95/p99、并发数、失败率和允许的结果误差。本题的资源阈值只保护教学实验，不是通用生产 SLA。若数据大到不适合物化，可考虑流式堆、外部排序或分区去重；跨分区首次顺序、I/O、持久化和合并成本必须另验，不能直接沿用此处数字。

## 延伸 / 追问

- **只看代码有两层循环就判 O(n²) 吗？** 不行，要看总迭代次数和提前退出条件。内层遍历长度 u、固定 k、几何增长或双指针不回退，都可能改变总工作量；本例双循环全同输入就只做线性数量比较。
- **哈希平均 O(1)，为何偶发慢请求仍存在？** 平均分布不保证单次延迟，扩容、碰撞链、长 key、分配器、GC 和系统调度都可能影响尾部。需要容量/输入限制和真实链路观测；本题三次本地内核计时不测尾延迟。
- **数据读不完或内存不足时怎么办？** 精确 Top-10 仍需看全部输入；有界堆可降低保留状态，但无法跳过未知数据。去重可用外部排序或分区，但输出顺序和边界去重也必须符合契约；近似结构需要先获得允许误差的需求，不能把 Bloom filter 当作精确去重器直接丢记录。

## 常见误区

- **“Big-O 就是秒数。”** 它描述渐近增长，不包含硬件、输入分布、常数、I/O 和内存层次；课程按固定操作速率换算的演示不能当作已跑数据。
- **“平均 O(1) 就是任意负载恒定延迟，均摊还能保证每次一样快。”** 分布假设、整串操作成本和单次最坏/尾延迟必须分开。
- **“只要返回数量一样，优化就成功；堆总比排序快。”** 首次/末次保留、稳定并列、排序方向都可能悄悄改变答案；算法实现和输入顺序也会改变测量排名。
- **“额外 O(k) 就是整机 O(k)，本地全绿就能上线。”** 物化输入、原生库分配和业务链路并未消失。这里没有生产用户数据、业务服务、真实负载或发布验收结果。
