## 问题

上下文感知检索（contextual retrieval，给每个 chunk 拼上文档级上下文再嵌入）能提升召回，但当原文结构混乱、过时或自相矛盾时，它会把"更好检索"的错误内容更精准地送进上下文，反而放大错误。如何在检索阶段就引入信息质量信号，而不是等生成阶段兜底？

## 答案

> 🤖 AI 答案 · 模型：Claude-Opus-4.8 · 日期 2026-08-06

**先看为什么会放大。** contextual retrieval 只优化"**这段内容和 query 有多相关**"，它对内容**对不对、新不新、可不可信**一无所知。于是一段过时或错误的文档，加了上下文后反而更容易被高分召回、更"言之凿凿"地进入 prompt——相关性越准，错的越稳。根因是**排序信号里只有相关性，没有质量**。解法：**把质量做成一等检索信号，让打分从 `score=相关性` 变成 `score=相关性 × 质量`。**

```
query ─► 召回候选 ─► 打分排序
                      │  旧：score = sim(q, chunk)
                      ▼  新：score = sim × f(质量信号)
        ┌─────────────质量信号───────────────┐
        │ 新鲜度：doc 时间戳 vs query 时效需求  │
        │ 来源可信：权威源/官方>UGC>爬取       │
        │ 冲突检测：与高可信源/多数意见是否矛盾  │
        │ 完整性：结构是否残缺、是否被腰斩       │
        └────────────────────────────────────┘
        ▼ 低质降权 / 打标 / 过滤，冲突则并呈让 LLM 裁决
```

**四类可落地的质量信号：**

1. **新鲜度（freshness）。** 给每个 chunk 带 `更新时间`，对时效敏感的 query（价格、版本、政策）按时间衰减降权旧内容；同一事实的新旧两版冲突时，新版优先，旧版降权但保留可追溯。

2. **来源可信度（source credibility）。** 在**离线入库**时给每个来源打权威分（官方文档 > 内部已核实 > 社区 UGC > 泛爬网页），检索时作为乘性权重。可信度是文档级元数据，不该等到检索时才现算。

3. **冲突检测（conflict detection）。** 召回后对 top-k 做一致性检查：同一实体/字段出现互斥断言时，别默默取最高分那条，而是**以高可信 + 高新鲜源为锚**给冲突方降权，或**把冲突证据并列呈交** LLM，附来源与时间，让它显式裁决而非蒙在鼓里。

4. **完整性 / 结构质量。** 结构混乱、被切碎腰斩、缺上下文的 chunk 降权；入库时的清洗、去重、结构化本身就是最省事的质量前置——**烂数据别进库**，比检索时补救便宜得多。

**分层落点：** 质量信号越早注入越省力——**入库期**做清洗/去重/来源打分/时间标注（治本），**检索期**做质量加权 + 冲突检测（治标兜底），**生成期**再让 LLM 带着来源/时间/冲突标注审慎作答（最后一道）。别把全部希望押在最后一层。

**一句话：** 检索排序不能只认相关性——**把新鲜度、来源可信度、冲突信号、完整性做成乘性质量权重**，让"错但相关"的内容被降权而非被精准放大，冲突就并呈交给 LLM 裁决。

## 延伸 / 追问

**追问：质量信号会不会误伤——把"小众但正确"的新观点当成低质压掉，形成对主流/旧源的偏见？**

会，所以质量加权要**可调、可解释、可绕过**，而不是一刀切的硬过滤。三点缓解：① **降权而非删除**——低质信号默认只降低排序权重、保留在候选里，别直接丢，避免"少数正确"被彻底屏蔽；真正过滤只留给明确的硬规则（如已知失效、已撤稿）。② **区分"可信度低"与"与多数不符"**——冲突检测判的是"和高可信源矛盾"，不是"和多数意见不同"；一个来自权威源的少数派结论不该因"少数"被压，权重应主要由**来源可信度 + 新鲜度**决定，而非"随大流"。③ **保留冲突、交由 LLM/人裁决**——对拿不准的冲突并呈证据（来源、时间、分歧点），让下游带着上下文判断，而不是在检索层替它拍死。此外用**离线评测集 + 线上反馈**持续校准质量权重，监控是否系统性压制某类正确但小众的来源，发现偏见就回调权重。
