## 问题

Coding Agent 靠"写代码 → 跑测试 → 看结果"闭环自我纠错。这个"执行后自动验证（execute-verify-feedback）"的思路，除了写代码跑测试，还能用在哪些 Agent 工具场景？每类的验证收益、成本和风险边界是什么？

## 答案

> 🤖 AI 答案 · 模型：Claude-Opus-4.8 · 回答 2026-08-06

**先抽象出通用范式。** "跑测试"只是一个特例，本质是：**动作产生可观测的真实反馈 → 拿反馈核对预期 → 不符则自我纠正**。凡是"动作有客观、可机读的成功标准"的工具场景，都能套这个闭环。

```
Agent 动作 ──► 副作用发生 ──► 采集真实反馈（回读/查询/断言）
   ▲                                    │
   └──── 不符预期→修正重试/回滚/升级 ◄───┘ 符合→继续
```

**可套用的场景（及各自收益/成本/风险边界）：**

1. **数据库变更**：执行后回读（`SELECT` 校验行数/字段值、比对影响行数与预期）。收益高、验证便宜。**风险边界**：`UPDATE`/`DELETE` 是有副作用的——验证要**前置**（先 dry-run/`EXPLAIN`/`COUNT` 估影响面），别"先删了再验证发现删多了"。

2. **文件操作**：写完回读校验内容/哈希/存在性、跑 lint/schema 校验。便宜、可逆性好（有备份即可回滚），适合大胆自动重试。

3. **UI / 浏览器自动化**：操作后截图 + 断言（元素出现、文案匹配、URL 跳转），或视觉回归。收益高但**成本高、脆**（页面异步、选择器易变），需重试与超时，验证本身可能误报。

4. **API 调用**：校验状态码、响应 schema、幂等地重查资源状态确认副作用生效。便宜可靠，是最适合自动闭环的一类。

5. **邮件 / 消息发送**：可验的是"是否投递成功"（provider 回执/bounce），**验不了"内容对不对、该不该发"**——发出即不可撤销。**风险边界**：这类**不可逆外发**应把关口前移到执行前（人工确认/护栏），事后验证只能收集投递结果，不能兜底"发错了"。

6. **支付 / 转账**：验证=对账（查交易状态、幂等键确认是否真扣款）。**风险边界最严**：绝不能靠"失败就重试"——重试可能重复扣款；必须幂等键 + 对账 + 人工审批，验证用于**确认最终态**而非驱动盲目重试。

**一句话判据：验证能否自动闭环，取决于两点——① 反馈是否客观可机读；② 动作是否可逆。** 可逆 + 可机读（DB 读、文件、API、UI 断言）→ 放心自动 execute-verify-retry；**不可逆**（转账、外发、删数据）→ 验证前移为执行前 gate + 事后对账确认最终态，绝不用"失败重试"当纠错手段。

## 延伸 / 追问

**追问：验证器本身也可能错（假阳性/假阴性），怎么防止"验证通过了其实没做对"或"其实做对了却反复重试"？**

关键是**别让生成方自己当唯一裁判**，并给验证器设可信度分层。三条：① **验证器与执行器解耦、用确定性手段优先**——能用精确断言（行数、哈希、状态码、对账金额）就不用 LLM 自评；LLM 自评易"自我确认"，只作辅助信号、不作最终放行。② **区分两类错误的代价**：假阴性（做对了却判失败）触发的是重试，对**不可逆动作**代价极大（重复转账）——所以不可逆动作必须幂等 + 对账，让重试安全或干脆禁止盲目重试；假阳性（没做对却判成功）会让错误静默流出，需靠**多重/交叉验证**（不同维度各查一次）降低漏判。③ **设重试上限 + 升级人工**：连续 N 次验证不过就停下来交人，别无限自纠——反复失败往往是任务理解或环境问题，不是重试能解决的。核心原则：**验证要独立、确定性优先、对不可逆动作从严，纠错有上限**。
