## 问题

“执行后自动验证”除了写代码跑测试，还能应用在哪些 Agent 工具场景？请结合数据库变更、文件操作、UI 自动化、邮件发送、支付等场景，说明验证的收益、成本与风险边界。

## 答案

> 🤖 AI 答案 · 模型：Claude-Opus-4.8 · 日期 2026-08-06

**本质：验证是把「工具返回值」升级为「对世界真实状态的独立复核」。** 工具返回 `200/OK` 只代表调用被接受，不代表副作用如预期发生。执行-验证-反馈闭环让 Agent 用一次**独立的读回**确认结果，再决定收尾、重试还是升级——这是所有有副作用的工具都该配的能力，写代码跑测试只是其中一例。

**通用套路**：动作 → 读回真实状态 → 与预期断言 → 命中则结束/不命中则修正。

| 场景 | 验证动作 | 收益 |
| --- | --- | --- |
| 数据库变更 | read-after-write、`affected_rows`、约束/行数校验 | 抓住写错行、静默失败 |
| 文件操作 | 重读内容、校验和、lint/parse | 防写坏、路径写错 |
| UI 自动化 | 截图/DOM 断言目标元素出现 | 防「点了但没生效」 |
| 邮件/消息 | 查投递回执、bounce 状态 | 确认真的送达 |
| 支付/转账 | 回查订单终态、对账 | 防重复扣款、状态不一致 |
| 基建变更 | health check、金丝雀探测 | 防上线即故障 |

**成本**：每次验证都要额外读回，带来延迟、调用费、token 和实现复杂度；对高频低风险动作全量验证并不划算。**按「误判代价 × 频率」定验证强度**——低风险抽样，高风险必验。

**风险边界（关键）**：验证策略要看动作**可逆性**。

```
可逆动作（DB 可回滚、文件有备份）
    → 执行 → 读回验证 → 失败即重试/回滚，闭环成本低

不可逆动作（支付、发邮件、发短信）
    → 事前 dry-run/预检 + 确认（幂等键、二次确认）
    → 事后只能「对账式验证」+ 告警/人工介入，无法靠重试兜底
```

对不可逆副作用，**验证的重心前移到执行前**（幂等、预演、审批），事后验证退化为对账与告警；盲目「失败就重试」反而会重复扣款、重复发信。**一句话**：凡有副作用的工具都值得配读回验证，但验证强度按风险定档，重试策略按可逆性设计。

## 延伸 / 追问

**追问：验证本身也可能失败或说谎（读到脏缓存、验证器有 bug），怎么防止 Agent 陷入「假验证」而误以为成功？**

三条原则：**① 验证要「独立于执行路径」**——别用写入时同一个连接/缓存去读回，尽量走主库或旁路只读通道，避免读到自己刚写的缓存假象；**② 验证也要有兜底**——验证超时/异常时按「未确认」处理并告警，绝不默认成功，宁可误报不可漏报；**③ 断言要具体、可证伪**——校验行数、关键字段、终态枚举等硬指标，而非「无异常即通过」，并给验证设最大重试与最终 SLA，防止验证环节自身死循环。核心：验证器的可信度也要被度量，高风险动作叠加人工抽检或双通道交叉核对。
