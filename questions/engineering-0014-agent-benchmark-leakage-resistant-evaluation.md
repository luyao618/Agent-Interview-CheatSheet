## 问题

公开 benchmark 一旦发布，很快会被抓进下一轮训练语料（data contamination），模型「见过答案」导致分数虚高、失去区分度。如何设计抗泄漏的 Agent 评估？

## 答案

> 🤖 AI 答案 · 模型：Claude-Opus-4.8 · 回答 2026-08-12

**先认清失效机制：** 公开测试集是**静态、有限、可被记忆**的。一旦进入训练语料，模型可能靠**回忆**而非**能力**答对，benchmark 就从「测能力」退化成「测记忆」——分数涨了，真实表现没变。所以抗泄漏的核心是让评估**不可被提前记忆**：要么题目每次新生成，要么答案从未公开。

```
静态公开集（会被污染）          抗泄漏设计
题目固定、答案已公开     →   ① 程序化动态生成（每次新实例）
一次泄漏、永久失效       →   ② 私有 holdout（从不公开）
只看最终答案对错         →   ③ 交互环境按状态判定
                         →   ④ 时间隔离（用训练截止后的新数据）
                         +   持续污染审计
```

**四类抗泄漏手段：**

1. **程序化动态生成（最治本）。** 用**生成器**而非固定题库：模板 + 随机参数、随机种子实时合成任务实例（改数值、改实体、改约束组合），并**自动算出真值**。模型背不下无限实例，记忆失效；同时能按难度维度可控地扩样本。

2. **私有 holdout / 盲测集。** 公开一个 dev 集供迭代，真正排名用**从不公开**的私有集，只回传聚合分、不回传逐题内容；提交式评测（模型跑在评测方环境里）比发数据集更抗泄漏。代价是需要维护方与算力。

3. **交互式环境评估（Agent 尤其适用）。** Agent 的能力是**在环境中达成目标**，不是答一道题。用可交互沙箱（真实工具、可变初始状态）按**最终状态/副作用**判定成功——环境随机化后，即便读过攻略也得真正执行；这类任务天然比 QA 难以靠记忆通关。

4. **时间隔离（temporal holdout）。** 用**模型训练截止日之后**产生的新数据/新事件构造任务，从时间上保证未被训练见过；配合定期滚动更新题库。

**配套：污染审计与治理。**
- **检测**：n-gram / 近重复比对测试样本与训练语料；**canary 串**（在集内埋唯一标记，若模型能复现即证明泄漏）；对比「原题 vs 改写题」的分差——分差异常大提示记忆而非理解。
- **治理**：题库**版本化 + 定期轮换**、公开即视为「已污染、待退役」、报告分数时标注题库版本与生成时间。

**一句话：** 抗泄漏评估的关键是把 benchmark 从「静态可记忆的题库」变成**「每次新生成的实例 + 从不公开的 holdout + 环境中判成败」**，并用污染检测与定期轮换持续兜底——**能被背下来的分数，不算能力**。

## 延伸 / 追问

**追问：动态生成的题目怎么保证「难度可比」——否则每次分数波动，还能横向比模型吗？**

关键是让随机化只作用于**表层实例**，不动**难度结构**。做法：① **参数化难度**——生成器显式声明难度因子（步数、干扰项数量、约束个数、需调用的工具数），同一难度档内只随机化表层内容（数值、实体名、顺序），保证同档实例**同构不同貌**。② **足够样本量**——单实例噪声大，用每档 N 个实例的平均分而非单题，配合置信区间报告，波动自然被摊平。③ **锚点校准**——每次评测混入一小组**固定锚点题**（可复用、非公开），用它们校准本轮生成集的难度漂移，类似考试的等值化（equating）。④ **回归验证**——新一版生成器上线前，用一组已知能力梯度的模型跑一遍，确认分数排序与历史一致，再投入使用。核心是：**随机化换的是「不可记忆」，不是「不可比较」**——只要难度维度被显式控制并统计化处理，横向比较依然成立。
