## 问题

RAG 处理图表、表格、界面截图时，若直接 OCR/caption 成纯文本，会把「谁在谁上面、哪列对哪行、箭头指向谁」这类**空间与层级关系**丢掉，检索和回答就答不准结构性问题。应如何保留这些视觉结构？

## 答案

> 🤖 AI 答案 · 模型：Claude-Opus-4.8 · 日期 2026-08-06

**先看丢在哪。** 纯文本抽取是把二维版面**拍扁成一维 token 流**：表格的行列对齐、流程图的连接方向、UI 的包含层级，全靠位置和线条承载，OCR 拉直后这些关系荡然无存。于是「第 3 季度华东的值」「A 之后接哪个节点」这类问题就无从检索。核心思路：**别只存"文字说了什么"，要一并存"它在版面里的结构"**——用结构化表示 + 保留原图双通道，而非二选一。

```
文档页 ──┬─► ① 版面/结构抽取  → 结构化文本(带 bbox/层级/表结构)
        ├─► ② 结构翻译       → Markdown表/HTML/mermaid，行列/连接显式化
        ├─► ③ 图 patch 直存   → 多模态 embedding（版面隐含在像素里）
        └─► ④ 图索引/关系图   → 节点+边（who-points-to-who）
   检索命中任一通道 → 回取「结构化文本 + 原图区域」一起喂给 VLM
```

**四条可组合的手段：**

1. **保留 layout metadata。** 抽取时带上每个元素的**边界框、阅读顺序、层级、所属区块**（用 Document AI / 版面分析模型，而非裸 OCR）。检索片段附着这些坐标，"上方/左侧/同一单元格"就能被还原和过滤。

2. **结构化抽取而非拉平。** 表格转成 **Markdown/HTML 表**（保住行列对齐与表头），流程图/架构图转成**节点-边的显式表示**（如 mermaid/邻接表），图表转成"标题+坐标轴+系列数据"的结构化字段。让空间关系变成**文本里可读的结构**，而不是散落的词。

3. **多模态 embedding + 原图直存。** 用 VLM/CLIP 类模型直接对**图像区域**做嵌入（ColPali 等页面级视觉检索），版面信息隐含在像素里、无需先转文字；同时把原图（或裁剪区域）存下，命中后连图一起回灌给多模态模型看，别只给它二手文字。

4. **图索引保关系。** 对流程图/知识图这类强关系内容，抽成**关系图（节点+有向边）**单独索引，支持"A 的下一步是什么""谁指向 C"的结构化查询，这是纯向量检索答不了的。

**检索与生成要闭环：** 无论命中哪个通道，回取时**把结构化文本和对应原图区域一并**送多模态模型，让它既读到结构、又能核对原图，避免"文字抽错了也无从发现"。

**一句话：把版面结构当一等信息**——layout metadata 存坐标层级、表/图转成显式结构、多模态 embedding + 原图直存、强关系走图索引，检索时**文本与原图双通道回灌**，视觉结构才不会在"转文字"那一步蒸发。

## 延伸 / 追问

**追问：全都做多模态 embedding + 原图直存最省事，为什么还要费力做结构化抽取？**

因为两条路各有盲区，互补才稳。**纯多模态检索**（页面级视觉嵌入）省去解析、对"长什么样"的模糊查询很强，但它给的是**整页/区域的相似度**，做不了精确的结构化过滤与聚合——"华东且 Q3 且 >100 万"这种按行列/字段的条件查询，靠像素相似度既不准也不可解释，且大图直存、逐页 VLM 调用的**存储与推理成本**高。**结构化抽取**把表/图变成可 SQL/可过滤的字段，精确、便宜、可审计，但解析会出错、对没有清晰结构的自由版面力不从心。实践是**分层**：能可靠结构化的（规整表格、明确流程图）走抽取，拿它做精确检索与聚合；结构混乱或"看图才懂"的走多模态嵌入 + 原图兜底；两者都建索引、检索时融合排序。用抽取保精度与成本，用多模态保召回与鲁棒，而不是指望单一通道通吃。
