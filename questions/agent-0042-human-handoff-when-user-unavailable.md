## 问题

Agent 需要人工接管但用户不在线或指令模糊时，系统该怎么设计？请说明优雅移交控制、等待 / 降级 / 冻结 / 继续低风险动作的决策策略、超时机制，以及信息收集与恢复执行。

## 答案 · Claude-Opus-4.8

> 🤖 AI 答案 · 模型：Claude-Opus-4.8 · 回答 2026-08-05

**先分清两种触发**：一是**高风险动作需授权**（转账、删数据、发对外邮件），二是**信息不足需澄清**（指令模糊、缺参数）。两者都指向"需要人"，但用户不在时的正确行为不同——前者宁可**停**，后者可以**先把能做的做完**。核心原则：**默认安全（fail-safe），可逆的往前推，不可逆的先冻结**。

```
需要人工介入
   │
   ├─ 保存 checkpoint（意图/已做/待决点/上下文）—— 移交的前提
   │
   ├─ 通知：按紧急度选通道（应用内 → 邮件 → 升级到备选审批人）
   │
   ▼ 用户不在？看待决动作的可逆性/风险
   ├─ 低风险·可逆   → 继续做（记审计），把阻塞点单独挂起
   ├─ 需澄清·非阻塞 → 走合理默认 + 标注假设，继续；模糊点留给复核
   ├─ 高风险·不可逆 → 冻结该分支，绝不猜着执行
   └─ 整体阻塞      → 进入等待，挂超时
        │
        ▼ 超时到期（分级）
        ├─ 短：重试通知 / 升级到他人
        └─ 长：安全降级——回滚未提交事务、释放锁、置为 pending，
               给用户一份"我做到哪、卡在哪、需要你定什么"的摘要
```

**四个设计要点：**

1. **优雅移交 = 可恢复的 checkpoint。** 移交不是把任务丢给人，而是把状态**外置**成人和 Agent 都能读的结构：原始目标、已完成步骤、当前待决点、可选项与推荐项、恢复所需上下文。没有它，人接手要重新理解、Agent 醒来无从续跑。

2. **决策策略按"可逆性 × 风险"分档。** 不可逆/高风险 → 冻结等授权；可逆/低风险 → 带审计继续；模糊但非阻塞 → 取**保守默认**并显式标注假设，把判断留到复核。别用"一律停"（可用性差）或"一律猜着干"（危险）一刀切。

3. **超时要分级、要有兜底动作。** 等待必须带 TTL，且超时不是无限重试：短超时重试通知 / 升级到备选审批人；长超时**安全降级**——回滚未提交事务、释放锁、把任务置为 `pending` 并产出摘要，避免半执行状态和资源长期占用。

4. **恢复执行靠幂等 + 断点续跑。** 人给出决定后，从 checkpoint 续跑而非重来；每步幂等（幂等键/去重），保证通知重发、重试、恢复都不会重复副作用。

**一句话**：把"需要人"变成一次**带状态快照的可恢复挂起**——可逆的继续、不可逆的冻结、等待挂超时、恢复靠幂等续跑，让"用户不在"退化成延迟而非事故。

> **要点**
> - 区分"需授权"与"需澄清"：前者宁停，后者可带默认继续
> - 移交的前提是可恢复 checkpoint（意图/进度/待决点/上下文）
> - 决策按"可逆性 × 风险"分档：可逆继续、不可逆冻结、模糊走保守默认
> - 超时分级 + 安全降级（回滚/释放锁/pending+摘要），恢复靠幂等续跑

## 延伸 / 追问

**追问：怎么防止"合理默认 + 标注假设"滑成 Agent 擅自替用户拍板？**

给"自动走默认"划死边界，而非交给模型自觉。三条闸：**一是可逆性红线**——只有可回滚、低影响面的动作允许走默认；触及金额、权限、对外副作用、生产数据的一律不许，必须等人。**二是假设必须显式且可追溯**——每个默认写进 checkpoint 与审计（"因未响应，按 X 处理，依据 Y"），复核时一眼可查、可推翻，而不是藏在执行里。**三是默认要保守、可撤回**——优先选影响最小、最容易 undo 的选项，并保留撤回窗口。本质是：默认只用来**降低阻塞**，不用来**替代授权**；凡是"错了就收不回"的决定，永远留给人。
