## 问题

工具集频繁变化（MCP server 上下线、按会话动态增删工具、工具定义时常改版）时，如何布局上下文，才能最大化 Prompt Cache 命中率？

## 答案 · Claude-Opus-4.8

> 🤖 AI 答案 · 模型：Claude-Opus-4.8 · 回答 2026-08-06

**先认清缓存的命门。** Prompt Cache 只对**逐字相同的前缀**命中，且工具定义（tool schema）通常拼在 system 之后、紧邻最前面。这意味着：**只要工具列表变一个字节，从那个位置往后的缓存全部失效**——而工具定义往往是 prompt 里很大的一块。工具集越频繁变，这块越常抖动，缓存命中率就越低。核心矛盾就是：**动态的工具集 vs 缓存要求的不变前缀。**

**布局总原则：按「变化频率」分层，越稳定的越靠前、越易变的越靠后。**

```
[稳定前缀 · 长期命中缓存]
  system / 角色 / 全局约束
  ── 核心工具目录：全程常驻、逐字不变、顺序固定的一组工具
[半稳定]
  按会话/任务加载的工具子集（会话内不再变）
[易变尾部 · append-only]
  动态注入的工具、当前可用性、运行时状态、对话历史
```

**五个具体手段：**

1. **稳定核心 + 按需注入。** 把高频通用工具固化成一个**逐字不变的核心目录**放前缀；小众/情境工具不塞进全局定义，而是**用到时才注入**到尾部或经二级检索披露。别把「全量工具」一股脑摊在前缀里随会话增删。

2. **顺序稳定化。** 工具在 prompt 里的**排列必须确定**（按 id 固定排序），不要用遍历 dict/set 得到的随机序——顺序一变，逐字前缀就变，缓存白丢。

3. **不删只标（软移除）。** 会话中途某工具下线时，**不要从前缀里物理删掉**（会击穿后面所有缓存），而是在**尾部**追加一条「工具 X 当前不可用」的状态说明。前缀不动，缓存保住。

4. **动态信息一律后置。** 时间戳、当前可用性、配额、运行时状态这类每轮都变的内容，绝不能混进工具定义块，统一放到 append-only 尾部。前缀里出现一个变动值，等于每轮都 miss。

5. **MCP / Skill 元数据分离。** 把「工具/技能的完整定义」与「当前挂载了哪些」解耦：稳定的能力**目录/命名空间**放前缀，具体启停、版本、来源等易变元数据后置。MCP server 上下线只动尾部的挂载清单，不动前缀目录。

**一句话：让工具定义块成为一段「逐字不变、顺序固定、只增不删」的稳定前缀**——核心工具常驻、小众工具按需披露、下线软标记、所有动态信息后置，把「工具集在变」隔离在缓存边界之外。

> **要点**
> - Prompt Cache 只认逐字前缀；工具定义在前缀里，一改就整体失效
> - 按变化频率分层：稳定核心工具前置、易变工具与状态后置
> - 顺序固定、下线软标记不物理删、动态元数据一律 append 到尾部
> - MCP/Skill：稳定能力目录放前缀，挂载清单/版本等易变信息后置

## 延伸 / 追问

**追问：如果核心工具本身也偶尔要改版（新增参数、改描述），怎么减少这类必然的缓存失效？**

思路是**把不可避免的失效做成低频、可摊薄的事件**。① **批量 + 择时改版**：不要零散地今天改一个明天改一个，攒到一起在一个版本窗口统一发布，让 miss 一次性发生，而非天天抖动。② **版本化前缀**：把工具定义块视为带版本号的不可变单元，改版即生成新前缀；新前缀在随后多轮里重新累积命中，把这次 prefill 成本摊到后续请求。③ **向后兼容优先**：能加可选参数就别改已有字段语义，减少「描述重写」这种大范围逐字变动。④ **改版隔离**：若只有个别工具频繁演进，把它从稳定核心里移出去、放到易变尾部按需注入，别让一个「爱变」的工具拖累整块核心目录的缓存。本质仍是那句话——**把易变的与稳定的分开，让缓存边界落在变化之前**。
