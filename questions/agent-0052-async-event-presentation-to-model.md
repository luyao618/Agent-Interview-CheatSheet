## 问题

异步 Agent 运行时，工具结果、用户新消息、系统提醒（超时、审批、护栏告警等）会并发到达并在一轮之间堆积。如何把这些异构事件组织进上下文喂给模型，才能让它抓住重点、正确决策，而不是只盯着最后一个事件？

## 答案 · Claude-Opus-4.8

> 🤖 AI 答案 · 模型：Claude-Opus-4.8 · 回答 2026-08-06

**核心矛盾：** 事件是「并发、异构、会堆积」的，而模型上下文是「线性、有限、有近因偏置」的。直接把原始事件流按到达顺序糊上去，模型只会盯着末尾那条、漏掉更重要的早到事件。组织策略要做四件事——**排序、分组、压缩、提级**，把无序事件流整理成一份「结构化简报」。

**1. 排序：语义优先，而非到达顺序。** 不要用 arrival time 排。按「决策相关度」重排：系统护栏/审批 > 用户新指令 > 关键工具结果 > 普通工具结果 > 状态类通知。同一优先级内再按时间。让最该被处理的事件靠近决策点（上下文末尾）。

**2. 分组：按来源/类型分区块，而非交错。** 把同类事件聚到一起，模型才能整体判断，避免语义割裂：

```
┌ SYSTEM (需先处理) ─────────────┐
│ ⚠ 审批待批：删库操作            │
│ ⚠ tool_call#7 超时（已重试1次） │
├ USER (新输入) ─────────────────┤
│ 用户追加：先别删，导出一份备份  │
├ TOOL RESULTS (本轮回灌) ───────┤
│ ✔ search×3 命中12条（详见下）   │
│ ✖ db_query 失败：连接超时       │
└ STATUS ────────────────────────┘
  目标 X | 步 4/6 | 预算 18/50
```

**3. 压缩：摘要 + 去重，控 token。** 堆积事件最容易撑爆上下文：
- **去重/合并**：3 次相同检索、重复的心跳/进度事件，折叠成一条带计数（`search×3`），只留代表性载荷。
- **摘要**：长工具结果（大 JSON、日志）先摘要留结论，原文按需展开或存到外部记忆给引用句柄。
- **有界**：每类事件保留最近 N 条并截断，旧的滚动进摘要，防止无限堆叠。

**4. 提级：关键事件显式高亮。** 对抗近因偏置的关键一招——**别指望模型自己在长列表里发现重点**。用显式标记（`⚠`/「需先处理」）、置于末尾、并在状态栏点名未决事项，把「有一个高优先事件在等你」这件事变成模型绕不开的显式信号。用户的新指令尤其要提级，因为它可能推翻正在执行的计划。

**一句话：** 把无序事件流当成待整理的 inbox——**语义排序、按类分组、去重摘要、关键提级**，交给模型的是一份「重点在前、结构清晰、长度有界」的简报，而不是一条按时间糊上来的原始流水。

## 延伸 / 追问

**追问：用户在工具执行中途发来新消息，是立刻打断当前动作，还是等这一步跑完再一起给模型？**

看该动作的**可中断性与副作用**。① **只读/可回滚**的动作（检索、读文件）——可软打断：让当前动作跑完或取消，下一轮把「用户新消息 + 已完成部分的结果」一起提级喂给模型重规划，代价低。② **有副作用/不可逆**的动作（转账、删数据、发邮件）——**不能中途丢弃**，务必等它到达一致状态（完成或安全回滚）再交给模型，否则会留下半执行的脏状态。工程上：给动作标 `interruptible` 属性，新消息先入队并打断点标记，在**轮边界**统一注入而非硬中断执行线程；紧急停止（用户喊「停」）走独立的高优先信号通道，直接触发取消与护栏，不排队。核心是把「响应及时」和「状态一致」分开：调度可以抢占，副作用必须原子。
