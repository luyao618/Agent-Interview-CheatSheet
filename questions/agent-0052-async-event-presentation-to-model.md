## 问题

异步 Agent 在一次决策前可能积压了一批异质事件：多个工具回调结果、新到的用户消息、系统提醒/告警、子 Agent 返回。若原样按到达顺序堆进上下文，模型往往只盯着最后一条、漏掉关键的。该如何组织这些事件再喂给模型？

## 答案

> 🤖 AI 答案 · 模型：Claude-Opus-4.8 · 回答 2026-08-06

**先认清失败模式：把"事件流"直接倒给模型有三个坑**——① **recency bias**：模型偏重最后几条，早到的关键事件被淹没；② **噪声淹没信号**：一堆低价值回调把真正要响应的用户消息挤没；③ **重复/过期**：同一状态被反复推送、旧告警已失效仍占篇幅。所以不能"按到达顺序 append 了事"，要**先编排再呈现**——把一批事件当一个"批次快照"来结构化组织。

```
积压事件（乱序·异质·可能重复）
   │ ① 去重/合并    同源同状态只留最新，压掉重复
   │ ② 分组         按类型/主题聚类（用户消息｜工具结果｜系统提醒｜子Agent）
   │ ③ 排序         组内按相关性/时间，组间按重要度（不是纯按到达）
   │ ④ 摘要         低价值/冗长事件压成一行，保留可回取引用
   │ ⑤ 高亮         关键事件（用户新指令、错误、超时）显式置顶/标注
   ▼
   [批次上下文块] 高亮项 + 分组摘要 + 明细（近/关键的留全文）
   +（可选）状态栏：本批做了什么、还差什么
```

**五个手段：**

1. **去重与合并。** 同一工具的多次回调、反复推送的同一状态，只留最新或合并成一条，别让重复事件反复刷屏、稀释注意力。

2. **分组而非流水账。** 按来源/类型聚类（用户消息、工具结果、系统提醒、子 Agent 结果），让模型一眼看清"有哪些类信息"，而不是在混排里逐条找。

3. **重要度排序 + 显式高亮。** 组间按重要度而非到达顺序：**用户新指令、错误、超时、高优告警**置顶并标注（如 `⚠️关键`）。对抗 recency bias 的关键就是"把重要的放到模型必看的位置并打标"，而不是指望它自己在长流里翻出来。

4. **分级摘要。** 冗长或低价值事件压成一行摘要 + 可回取引用（id/链接），近处和关键事件保留全文。既省 token 又不丢"能追回细节"的能力。

5. **状态增量而非全量重述。** 配一小块"本批变化"状态：这批事件让进度/待办发生了什么改变，而不是把整份历史重述一遍——让模型聚焦"新增了什么、现在该做什么"。

**一句话：** 把积压事件当一个**需要编排的批次**，先去重、分组、按重要度排序、分级摘要、关键项高亮，再连同状态增量一起呈现——用"结构化的批次快照"替代"按到达顺序的流水账"，模型才不会只盯着最后一条、漏掉真正要响应的事件。

## 延伸 / 追问

**追问：这套编排（分组/摘要/重要度打分）本身该由规则做还是 LLM 做？会不会太重？**

分层，别把每批都丢给 LLM 重排。**结构性操作用规则/代码**：去重（按事件指纹）、分组（按类型/来源）、时间排序、格式化——确定、快、零成本，覆盖绝大多数编排工作。**重要度与摘要**里，能规则化的先规则化：用户消息 > 错误/超时 > 普通工具结果这类优先级、按类型套摘要模板，都可硬编码。只有**语义判断**才升级给 LLM：一段自由文本告警到底急不急、几条事件能否合并成一句结论——且尽量用小模型、对结果缓存。为什么别全交 LLM：编排在每轮决策的热路径上，每批都过一次大模型既慢又贵，还引入不确定性（可能把关键事件摘掉）。稳妥做法是**规则搭骨架、LLM 补语义**，并对"摘要是否丢了关键信息"设护栏——高风险事件（错误、用户指令、涉钱操作）永远保留全文、不被摘要吃掉。这与事件优先级判定同理（见 engineering-0009）：规则主干、LLM 只补语义空缺。
